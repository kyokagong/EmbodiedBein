07 · Deployment

部署与真机遥测

从「训练出一个 checkpoint」到「机器人在地上走起来」之间，有一段最容易出事、 却最少被工具支持的路。这一章定义这段路的产物规范、放行流程与安全边界—— 以及一条必须守住的红线：平台不参与实时控制。

词表 Bundle / G5 比对的是部署时选用的本体环境。 机型挂在本体下，标定仍绑 RobotInstance。

7.1 先划红线：平台不做什么

这是本章最重要的一条设计决策 平台永远不进入实时控制回路。 它不发送关节指令、不读取实时状态用于闭环、不成为控制链路上的任何一环。 平台只做三件事：把策略包交付到机器人端、把遥测收回来、把这两件事记录下来。

为什么必须这样

  • 延迟不可控：本体控制环在 25–1000 Hz，任何经过 Web 服务、Python GIL、 TCP 重传的路径都无法保证时序。一次 50 ms 的抖动就可能让机器人摔倒。
  • 故障域隔离：如果平台崩了、Postgres 连接池满了、有人在浏览器里点了个大查询， 机器人不应该有任何感知。把平台放进控制回路等于把 Web 服务的可用性 变成机器人的安全前提。
  • 本体本来就是自洽的：仓库里的低层控制已经通过 UDP/CAN/串口 自成闭环， 它不需要平台。硬塞进去只会增加失效点。
  • 责任清晰：出事时能立刻分清是策略问题、控制器问题还是平台问题。
这条红线的代价与收益 代价：不能在 Web 上「一键让机器人走两步」，演示性稍弱。
收益：平台可以随意重启、升级、改架构，机器人不受影响； 也不需要为平台做实时性保证（这会波及整个技术栈选型）。 结论：收益远大于代价。如果将来确实需要 Web 遥操作， 应该做成一个独立的、旁路的轻量服务，而不是塞进这个平台。

7.2 策略包（PolicyBundle）

策略包是训练与真机之间的唯一交付物。它必须自包含、可校验、可追溯—— 拿到一个包就能知道它是什么、从哪来、能装在哪台机器上、是否通过了门禁。 

# bundle 目录结构（打包为单个 .ebp = tar.zst）
pb_01JB9F2K7X/
├── manifest.yaml          # 唯一必读入口
├── policy.onnx            # 或 policy.pt（TorchScript）
├── policy_meta.yaml       # 沿用仓库 policy_latest.yaml 格式，向后兼容
├── normalization.npz      # obs 均值/方差（若训练时用了归一化）
├── gate_report.json       # 放行证据：过了哪些门禁、实测值
└── SIGNATURE              # 对上述文件的 sha256 清单 + 签名

# manifest.yaml
api_version: eb/v1
kind: PolicyBundle
metadata:
  id: pb_01JB9F2K7X
  name: biped_walk_25hz
  version: "0.3.1"
  created_at: "2026-08-20T09:14:02Z"
spec:
  contract_id: ec_bhl_biped_12dof_v1     # 决定能装在哪台机器上
  runtime:
    format: onnx
    opset: 17
    providers: [CPUExecutionProvider]     # 上位机可能无 GPU
    policy_hz: 25
    measured_latency_ms: { p50: 2.9, p95: 4.1, p99: 6.8 }
  io_signature:                        # 冗余存一份，便于装机前离线校验
    obs_dim: 45
    act_dim: 12
    obs_layout: [velocity_commands:3, base_ang_vel:3, projected_gravity:3,
                 joint_pos_rel:12, joint_vel_rel:12, last_action:12]
    action_type: joint_position_offset
    action_scale: 0.25
  provenance:
    run_id: run_01JB6R1M9P
    model_version: mv_01JB6R4T2C
    code_ref: "bhl@a1b2c3d"
    image_digest: "sha256:4e9c…"
    data_version: "—（纯 RL，无外部数据）"
    asset_version: bhl-hw-v1.2
    seed: 1
  requires:
    calibration: { min_version: 4, max_age_days: 30 }
    firmware: ">=0.9.2"
  safety:
    action_clip: 0.30                    # rad，运行时硬限幅
    max_cmd_vel: { lin: 0.6, ang: 0.8 }
    watchdog_ms: 80                     # 推理超时则回落到保持姿态
    fallback: hold_pose
  gates_passed: [g_export_signature, g_sim2sim_consistency, g_latency_budget]
manifest 的三段结构 能不能装（contract_id / requires / io_signature）、 从哪来（provenance 五元组）、 怎么安全地跑（safety）。 三段齐全才允许打包，缺任一段直接拒绝—— 这样就不可能出现「不知道来源的策略被装上机器人」。
safety 字段不是建议值 action_clip、max_cmd_vel、watchdog_ms 由机器人端 runtime 强制执行，而非平台。平台只负责把它们写进包里。 如果 runtime 忽略这些字段，那么整套安全设计就形同虚设—— 所以 runtime 侧的实现是必要配套（见 7.6）。
为什么保留 policy_meta.yaml 仓库里已有 policy_latest.yaml 的消费方（低层控制侧读它拿关节顺序等）。 策略包原样保留这个文件，使得现有 runtime 不改也能用包里的策略， manifest.yaml 是增量的元信息层。 这样迁移成本接近零，也不会出现「两份真相」——manifest 的 io_signature 在打包时会与 policy_meta 交叉校验，不一致就打不出包。
签名的现实定位 单机内网环境下签名不是为了防攻击，而是为了防意外： 防止有人手工把一个 .onnx 拷进包里、防止传输截断、 防止「我以为装的是 v0.3.1」。用本地密钥做 HMAC 即可，无需 PKI。

7.3 三段放行流水线

导出段的关键细节

必须做 ONNX vs PyTorch 数值比对。 导出过程中的算子替换、动态形状处理、精度差异都可能引入偏差， 而这种偏差在训练日志里完全看不到。 做法：随机采样 256 组合法观测，两边各跑一遍，比最大绝对误差。 这一步成本几秒，能拦住一类非常难查的 bug。

sim2sim 段为什么用 ONNX 而非 checkpoint

仓库里的 play_mujoco.py 可以加载策略，但如果它加载的是 PyTorch 模型， 那么验证的就不是将要上机的那个东西。 强制用导出后的 ONNX 跑 MuJoCo，才能让这道门禁真正覆盖导出环节。 这是一个小改动、大收益的约束。

分级放行为什么必须人工确认

S0→S1→S2 的每次晋级都需要现场有人按下确认—— 因为「机器人是否被吊起」「保护绳是否挂好」这些前提平台无法验证。 平台的作用是：把检查项列清楚、把每级的遥测记录下来、 不让人跳级（S1 未通过则 S2 按钮不可点）。

7.4 机器人实例与 Fleet 台账

即使只有一台机器人，也需要台账。因为「这台机器现在跑的是哪个策略、上次标定是什么时候、 哪个电机换过」这些信息，在出问题时是排查的起点，而靠记忆一定会出错。

硬件变更是被低估的坑 更换一个电机后，零位、减速比标定、甚至质量分布都可能变， 而策略是在旧参数上训练的。平台把「维护记录」变成强制门禁的输入： maintenance_log 有新条目但 calibration 未更新时， 所有放行请求直接被拒。这条规则听起来烦人，但它防的正是那种 「机器人突然表现变差，查了三天发现是上周换过电机」的情况。

7.6 实现要点与必要的端侧配套

机器人端需要一个薄 agent

平台侧设计再完整，也需要端上有个东西来接包、执行限幅、上报遥测。 这个 eb-robot-agent（仓库目录 robot-agent/） 应当极简：

  • 拉取/接收 .ebp 包，校验签名与 manifest，落到本地目录
  • 把 safety.* 转成运行时约束交给控制进程（限幅、看门狗、fallback）
  • 采集控制环统计与硬件状态，本地聚合后批量上报（不做逐帧上传）
  • 维护 active 与 previous 两个包，支持本地一键回滚

关键约束：这个 agent 与控制进程不在同一个实时线程， 它崩溃不能影响控制。用独立进程 + 共享内存/文件交换即可。 代码量估计几百行，用 Rust 写以避免 GC 与依赖问题。

诚实说明：这部分依赖上游改动 策略包的 safety 字段要真正生效，需要低层控制侧读取并执行。 如果暂时不改，那么 action_clip 等字段就只是记录用途， 安全性仍完全依赖现有的硬件 E-stop 与人工看护。 平台设计上不假装这个问题不存在，而是在 UI 上显式标注 safety 字段未被端侧强制， 避免给人虚假的安全感。

遥测的存储与降采样

数据频率保留
控制环统计（p50/p99/丢帧）1 Hz 聚合原始 30 天，之后 1 min 聚合永久
关节温度/电流1 Hz同上
事件（E-stop / 摔倒 / 回滚）事件驱动永久（PG 行）
异常前后状态快照触发式 ±5 sCAS，永久
逐帧全状态不常态采集仅调试期开启，7 天 TTL

触发式快照是性价比最高的一项：平时不存，出事时能拿到前 5 秒的完整状态。 实现上端侧维护一个环形缓冲区，检测到异常就落盘。 这比「全都存下来然后从没人看」实用得多。

回滚必须是本地能力 回滚按钮在平台 UI 上，但实际回滚由端侧完成—— 端上一直保留 previous 包，回滚不需要网络。 这样即使平台不可达、网络断了，现场的人也能通过端侧命令回滚。 任何安全相关的操作都不能依赖网络。
与现有工具的关系 仓库里的遥操作、play_mujoco、低层控制脚本继续直连使用， 平台不取代它们。平台的定位是记录与治理： 你用什么工具跑都行，但产物与结果要进台账。 这个定位让平台不会成为你干活时的障碍。
