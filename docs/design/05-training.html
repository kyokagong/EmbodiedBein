05 · Training & Orchestration

任务编排与训练可视化

这一章是平台每天用得最多的部分。核心难点有三个： 把两套语义完全不同的训练栈统一到一个 JobSpec、 在只读仓库上跑会写仓库的脚本、 以及让 4 张卡在多个实验之间不打架。

5.1 栈适配器

Adapter 是唯一知道「底层脚本长什么样」的地方。它的输入是与栈无关的 JobSpec， 输出是三样东西：命令行、挂载表、环境变量表。 这个边界让上游仓库升级时的改动被限制在一个文件里。 

# backend/eb/adapters/base.py
class Adapter(Protocol):
    kinds: frozenset[str]                  # 它能处理的 JobKind

    def validate(self, spec: JobSpec, ctr: Contract) -> list[Violation]: ...

    def plan(self, spec: JobSpec, ctx: PlanContext) -> ExecPlan: ...
        # ExecPlan = {
        #   image, workdir, argv[],
        #   mounts[]:  (src, dst, ro|rw)
        #   env{},
        #   writable_paths[]:  仓库内需要打洞为可写的相对路径
        #   outputs[]:  产物认领规则（glob + kind + 保留策略）
        #   metrics:    指标来源声明（tfevents 路径 / stdout 正则）
        #   probes[]:   健康探针（如「10 分钟内必须出现第一个指标点」）
        # }

    def parse_progress(self, line: str) -> Progress | None: ...
        # 从 stdout 抽取「当前第几步 / 共几步」，用于进度条与 ETA

③ 镜像版本线不一致：宿主 pyproject.toml 是 isaaclab 2.3.2，而训练容器内是 0.54.3 + rsl-rl-lib 5.0.1。 Adapter 必须校验「JobSpec 声明的 image 的能力矩阵是否支持该 task」，不能假设两者相同。

5.2 工作区隔离

这是本设计里最「脏」但最必要的一块。上游脚本假设自己在一个可写的仓库里运行， 而平台要求仓库只读（为了复现与并发安全）。解法是精确打洞： 只把脚本确实要写的少数路径覆盖为可写卷，其余保持只读。

为什么不用 OverlayFS OverlayFS 更优雅（真正的写时复制），但需要额外权限且在容器内嵌套时有已知坑。 Docker 的挂载覆盖已经够用：给 logs/、configs/、outputs/ 三个子路径各加一个 rw 挂载即可，代价是要显式列出这些路径（writable_paths）。 这个列表由 Adapter 维护，一共不到十条，且有测试守护。如果将来上游脚本新增写入位置， 症状是明确的 Read-only file system 报错，很好定位。

队列策略

排序

主键 priority 降序，同优先级按提交时间升序（FIFO）。 加老化因子：等待每满 2 小时有效优先级 +5，上限 +25，防止低优先级任务被永久饿死。

优先级约定

90门禁与发布相关（sim2sim、导出）
70评估（短、结论驱动决策）
50常规训练（默认）
30Agent 自动探索
10数据处理批任务

短任务优先级高是刻意的：它们能快速给出结论，长时间训练晚开始几分钟无所谓。

抢占规则

  • 只抢 preemptible: true 的任务
  • 且必须已产出至少一个 checkpoint（否则抢了等于白跑）
  • 抢占前发 SIGTERM 并等 120 s 让其存 checkpoint
  • 被抢任务重新入队，attempt+1，自动带上 resume_from
  • Agent 提交的探索任务默认 preemptible: true

5.5 Pipeline DAG

Pipeline 把一串 Job 串成可复用的模板。它解决的问题是： 「训练完自动跑评估，通过就自动导出并跑 sim2sim」这套动作不该每次手动做。 

api_version: eb/v1
kind: Pipeline
metadata: { name: rl-to-bundle }
spec:
  contract_id: ec_bhl_biped_12dof_v1
  params:                        # 模板入参
    seeds: [0, 1, 2]
    max_iterations: 6000
  nodes:
    - id: train
      kind: train.rl
      fanout: { by: params.seeds }
      params: { task: Velocity-…-Biped-v0 }

    - id: pick_best
      kind: select
      needs: [train]
      params: { metric: "Train/mean_reward", mode: max }

    - id: eval
      kind: eval.sim
      needs: [pick_best]
      params: { suite: suite_biped_locomotion_v2 }

    - id: gate_a
      kind: gate
      needs: [eval]
      params: { gate: gate_locomotion_quality }
      on_fail: stop            # stop | continue | notify

    - id: export
      kind: export.policy
      needs: [gate_a]

    - id: s2s
      kind: eval.sim2sim
      needs: [export]
      fanout: { by: "range(8)", max_parallel: 8 }

    - id: gate_c
      kind: gate
      needs: [s2s]
      params: { gate: gate_sim2sim_regression }

    - id: bundle
      kind: bundle.build
      needs: [gate_c]
      params: { sign: true }

    - id: report
      kind: report.render
      needs: [bundle]
      params: { template: release_note, share: internal }
DAG 引擎的三条实现原则 ① 幂等重入：任何节点可单独重跑，已完成的上游不重算（按 spec_hash + 输入 artifact hash 判定缓存命中）。 ② 无中心状态机：节点状态由 Job 状态推导，DAG 引擎只做「谁可以跑了」的判断，避免两套状态不一致。 ③ 部分失败可续：fanout 里 8 个 seed 有 1 个失败，默认继续（可配 min_success）， 在报告里标注样本量减少——比整条流水线失败有用得多。

5.7 断点续训、重试与健康探针

续训

  • Isaac：--resume --load_run <dir> --checkpoint model_N.pt，平台把 run_id 解析为快照路径
  • RLinf：runner.resume_dir=…/checkpoints/global_step_N
  • 续训产生新 Run（attempt+1）但归属同一 Job，指标曲线在 UI 上按 step 自动拼接
  • 拼接处标注竖线，避免把「续训抖动」误读为算法问题

重试

  • 仅对 retry_on 列出的原因码自动重试（默认 infra_failed、oom）
  • OOM 重试时自动降参：num_envs ×0.75 或 micro_batch_size −1，并记录调整
  • exit_nonzero 默认不重试——代码 bug 重试只是浪费卡
  • 重试次数用尽后进入失败知识库并通知

健康探针

  • 启动探针：N 分钟内必须出现第一个指标点（Isaac 默认 15 min，含 shader 编译）
  • 停滞探针：指标 step 连续 M 分钟不前进 → 告警（不自动杀，可能是正常的长评估）
  • NaN 探针：loss 出现 NaN/Inf 立即告警并建议停止
  • 吞吐退化：SPS 相比前 30 min 均值掉 >40% → 告警（通常是内存泄漏或磁盘变慢）
探针不自动杀任务 除 NaN 之外，探针只告警不自动终止。原因很实际：训练里有大量看起来像卡住的正常状态 （长评估、checkpoint 写盘、环境重置），误杀一个跑了 8 小时的任务代价远大于多等 10 分钟。 自动终止的权限只交给显式的 timeout 与用户/Agent 的主动决策。

5.8 实现要点

Adapter 的测试策略（重要）

Adapter 是最容易随上游漂移的代码。防护手段是命令行快照测试： 

# tests/adapters/test_isaaclab_snapshot.py
def test_train_rl_command(snapshot):
    spec = load_fixture("train_rl_humanoid.yaml")
    plan = IsaacLabAdapter().plan(spec, ctx=FakeCtx())
    # 命令行、挂载表、env 全部纳入快照
    snapshot.assert_match(plan.to_canonical_text())

任何 Adapter 改动都会让快照 diff 出现在 PR 里，评审时能直接看到生成的命令变了什么。 再配一个 --dry-run 的集成测试，真正启动容器但把训练命令换成 --help， 验证挂载与环境变量确实可用。

调度器主循环

async def scheduler_loop():
    while True:
        snap = await ebd.resource_snapshot()      # GPU/CPU/mem/disk
        async with advisory_lock("scheduler"):    # PG advisory lock，防双实例
            for job in await queued_jobs_ordered():
                verdict = admit(job, snap)
                if verdict.ok:
                    lease = await reserve(job, verdict.gpus)   # 事务内写 ResourceLease
                    await ebd.start_run(job, lease)
                    snap = snap.minus(verdict)               # 本轮内立即扣减
                else:
                    await record_block_reason(job, verdict.reason)
        await asyncio.sleep(2)

2 秒轮询而非事件驱动：单机队列规模很小（几十个），轮询实现简单且不会漏事件。 ResourceLease 在事务里创建，避免两个任务同时认为同一张卡空闲。

指标归一化（跨栈统一命名）

采集器的一个关键细节 tfevents 是追加写的 protobuf 记录流。采集器按文件 offset 增量解析并持久化 offset， 这样 ebd 重启后不会重复导入指标（幂等）。 但要注意：训练进程可能在写入中途被杀，留下半条记录。解析器必须能识别截断的 record 并在下次有新数据时重试，而不是把整个文件判为损坏。
