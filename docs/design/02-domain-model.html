02 · Domain Model

领域模型、本体环境与接口

这是全平台的共享语言。所有模块页都会引用这里定义的实体与状态机。 接口数字的一等实体已从 Embodiment Contract 换成 本体环境（归属某个本体；Job 引用 ee_*）。 本节保留 G1–G5 与 JobSpec 形状；分层、纳管、CRUD、RLinf 四元组以 12 章为准。

2026-08-24 替换 「契约」不再是产品实体名。ER 图里的 EmbodimentContract ★ 读作 EmbodimentEnv ★，父级增加 Embodiment。 词表与 SQL 过渡见 12.md。 下文若仍写 contract / ec_*，一律视为 ee_* 的兼容别名。

2.1 实体总览

24 个核心实体，分为六个域。域内高内聚，域间只通过少量明确的引用连接—— 这个边界同时也是未来拆分服务的边界。

为什么用 ULID 而不是自增或 UUIDv4

  • 时间有序 → 主键索引局部性好，且「按 id 排序」等于「按创建时间排序」，省一个索引
  • 无需数据库往返即可在应用层生成 → 幂等提交时客户端可预生成
  • 不泄露总量（自增会）
  • Base32 无易混字符，口头/截图传达不易出错

本体、本体环境与 Dataset 采用人工语义命名——它们数量少、生命周期长、需要人反复引用。

2.2 本体环境规范（原 Embodiment Contract）

真源已迁到 12 章 分层、BHL 纳管、草稿 CRUD、3D、RLinf 四元组见 12。 下面保留四份接口数字与 G1–G5 表，作为实现对照；YAML 字段名过渡期内可仍出现在 contracts/*.yaml。
这个机制解决什么 Berkeley Humanoid Lite 现有四套并行的接口：humanoid 75/22、biped 45/12、 WBC 85/22、fixed-hand 10(+图像)/10，控制频率分别是 25/25/50/20 Hz。 这些数字目前分散在 env_cfg.py 的观测项列表、rsl_rl_ppo_cfg.py、导出的部署 YAML、 以及 C++ 侧的 N_JOINTS 常量里。任何一处不一致，症状都是「机器人抽搐」或「策略输出全零」， 而排查要花几小时。Contract 把这些数字收敛到单一真源，并在五个卡口自动比对。

# backend/eb/contracts/validator.py（核心逻辑示意）
@dataclass
class CheckResult:
    passed: bool
    violations: list[Violation]          # 每条含 path / expected / actual / hint

def validate_job(spec: JobSpec, ctr: Contract, ctx: Context) -> CheckResult:
    v = []
    # ① 任务名必须在契约声明的绑定里
    if spec.task and spec.task != ctr.sim_bindings.isaac_task:
        v.append(Violation("task", ctr.sim_bindings.isaac_task, spec.task,
                           hint="契约与任务不匹配，可能选错了 contract_id"))
    # ② 数据集兼容性（G2 时已算好，此处只查缓存标记）
    for dsv in ctx.dataset_versions:
        if ctr.id not in dsv.compatible_contracts:
            v.append(Violation(f"datasets[{dsv.id}]", ctr.id, dsv.compatible_contracts,
                               hint="该数据集动作维度与本契约不符，需先做重定向"))
    # ③ 基座模型
    if ctx.base_model and ctx.base_model.contract_id != ctr.id:
        v.append(...)
    # ④ 契约自洽（频率、维度求和）——启动时已校验，此处兜底
    v += ctr.self_assertions()
    return CheckResult(not v, v)
预期收益（可度量） 设立这个机制的目标是把「维度类错误」的平均发现时间从数十分钟（要等仿真起来）压到秒级， 并让此类错误在提交阶段就不可能入队。平台应统计「G1–G5 拦截次数」作为核心价值指标之一， 在 Showcase 里展示。 契约页要画的观测条带、关节树、G1–G5 引用矩阵见 11 · 契约工作台，本页不重复画面。

JobKind 与 Pipeline 节点 kind 是两套命名空间 上表 18 项是可下发的容器化任务。而 Pipeline 里还会出现 select（按规则挑选上游产物）与 gate（门禁判定）两类节点—— 它们不起容器，由编排器在控制面内直接求值，因此不占 GPU、不进队列、不产生 Run。 实现上二者共用 DAG 数据结构但走不同的执行路径， 不要把它们混进 JobKind 枚举，否则调度器会试图为它们分配资源。

2.4 状态机

Job 是意图，Run 是尝试。一个 Job 可以产生多个 Run（重试、抢占后重跑）， 但 Job 只有一个最终结论。这个区分让「重试 3 次终于成功」既能如实记录， 又不会污染实验成功率统计。

失败原因码（写入 Run.abort_reason） oom · cuda_error · gpu_lost · image_pull_failed · submodule_missing · contract_mismatch · dataset_unavailable · disk_full · timeout · user_cancelled · preempted · exit_nonzero · ray_bootstrap_failed · vulkan_unavailable。 每个原因码在失败知识库里对应一条诊断卡片与建议动作，供 Agent 直接消费。
幂等与并发控制 提交携带 Idempotency-Key（默认取 spec 规范化后的 hash）：相同 key 在 24 h 内重复提交返回原 Job。 状态变更使用乐观锁（version 列 + UPDATE … WHERE version = ?）， 避免调度循环与事件消费者同时改写造成状态回退。

2.5 血缘模型

血缘用单张通用边表而不是每对实体一张关联表。理由：查询模式是「从任意节点出发做 N 跳遍历」， 通用边表配合递归 CTE 就能一次查完，而多表 join 会随实体类型增长而爆炸。 

-- 通用血缘边（PostgreSQL）
CREATE TABLE lineage_edges (
  id            bigserial PRIMARY KEY,
  src_type      text NOT NULL,          -- dataset_version | model_version | run | artifact | bundle …
  src_id        text NOT NULL,
  dst_type      text NOT NULL,
  dst_id        text NOT NULL,
  relation      text NOT NULL,          -- consumed_by | produced | derived_from | evaluated_by | signed_into | deployed_to
  run_id        text,                      -- 产生这条边的执行（可空：人工登记）
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (src_type, src_id, dst_type, dst_id, relation)
);
CREATE INDEX ON lineage_edges (src_type, src_id);
CREATE INDEX ON lineage_edges (dst_type, dst_id);

-- 「这个上机策略的全部来源」：反向 N 跳遍历
WITH RECURSIVE up(t, i, depth, rel) AS (
  SELECT src_type, src_id, 1, relation FROM lineage_edges
    WHERE dst_type = 'bundle' AND dst_id = 'bdl_01JB…'
  UNION ALL
  SELECT e.src_type, e.src_id, up.depth + 1, e.relation
    FROM lineage_edges e JOIN up ON e.dst_type = up.t AND e.dst_id = up.i
    WHERE up.depth < 12
)
SELECT DISTINCT * FROM up ORDER BY depth;
血缘的三个高价值用途 ① 影响分析：某数据集发现标注错误 → 一次查询列出所有受影响的模型、评估与已发布 Bundle，逐个打标。 ② 叙事展示：Showcase 的核心视图就是这张图的可视化， 同事顺着看一遍就知道产出是怎么来的。 ③ 复现：给定任意产物，反向遍历即可重建完整的重跑脚本。

2.8 数据库 schema 要点

-- 只列出体现设计意图的部分；完整 DDL 由 Alembic 管理

-- 过渡：embodiment_contracts 可做成 embodiment_envs 的视图；见 12.md §6.2
CREATE TABLE embodiment_envs (
  id           text PRIMARY KEY,                 -- ee_bhl_humanoid_22dof_v1
  embodiment_id text NOT NULL,
  spec         jsonb NOT NULL,
  spec_hash    text  NOT NULL,                    -- 已发布禁止原地修改
  status       text  NOT NULL DEFAULT 'draft',
  aliases      text[] NOT NULL DEFAULT '{}',     -- 含 ec_*
  obs_dim      int GENERATED ALWAYS AS ((spec->'observation'->>'dim')::int) STORED,
  action_dim   int GENERATED ALWAYS AS ((spec->'action'->>'dim')::int) STORED,
  policy_hz    int GENERATED ALWAYS AS ((spec->'control'->>'policy_hz')::int) STORED
);

CREATE TABLE jobs (
  id            text PRIMARY KEY,
  experiment_id text REFERENCES experiments(id),
  contract_id   text NOT NULL REFERENCES embodiment_envs(id),   -- 过渡列名；应用层等同 embodiment_env_id
  kind          text NOT NULL,
  spec          jsonb NOT NULL,
  spec_hash     text NOT NULL,
  idem_key      text,
  status        text NOT NULL,
  priority      int  NOT NULL DEFAULT 50,
  version       int  NOT NULL DEFAULT 1,        -- 乐观锁
  attempts      int  NOT NULL DEFAULT 0,
  created_by    text NOT NULL,                     -- principal：user:kk 或 agent:autopilot
  gpu_seconds   bigint NOT NULL DEFAULT 0,      -- 预算账本累计
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (idem_key)
);
CREATE INDEX ON jobs (status, priority DESC, created_at);   -- 调度出队热查询
CREATE INDEX ON jobs USING gin (spec jsonb_path_ops);

CREATE TABLE artifacts (
  id         text PRIMARY KEY,
  sha256     text NOT NULL,                       -- 内容 id；同内容可多次登记
  kind       text NOT NULL,                       -- checkpoint | onnx | video | metrics | dataset | bundle
  size_bytes bigint NOT NULL,
  storage    text NOT NULL,                       -- cas://… 或 s3://…
  run_id     text REFERENCES runs(id),
  meta       jsonb,                                -- onnx 的输入输出形状就存这里，供 G3 使用
  refcount   int NOT NULL DEFAULT 0,             -- GC 安全
  pinned     bool NOT NULL DEFAULT false          -- 已发布产物永不回收
);
CREATE INDEX ON artifacts (sha256);

CREATE TABLE audit_log (                          -- append-only，无 UPDATE/DELETE 权限
  id         bigserial PRIMARY KEY,
  at         timestamptz NOT NULL DEFAULT now(),
  principal  text NOT NULL,
  action     text NOT NULL,
  subject    text,
  before     jsonb, after jsonb,
  trace_id   text,
  approval_id text
);
为什么 spec 用 jsonb 而不是拆成列 JobSpec 的字段会随 Adapter 增加而频繁扩展。拆列意味着每加一个参数就要一次迁移。 折中方案：需要索引/约束的少数字段提升为生成列或独立列（embodiment_env_id、kind、status、priority）， 其余留在 jsonb 里并建 GIN 索引。这样既能查 spec @> '{"params":{"num_envs":4096}}'，又不牺牲关键约束。
指标为什么不进 PG 一次 6000 iteration 的训练，20 条曲线 = 12 万点；十几个并行实验就是百万级行。 PG 能存但查询与前端对比会很慢，而且这些数据是只追加、按 run 分区、可丢弃的—— 正是段文件时序的理想场景。PG 里只保留每个 run 的指标索引（有哪些 metric、step 范围） 与终值摘要（final/best 值），供列表页排序与筛选。
