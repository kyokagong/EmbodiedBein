08 · Agent

Agent 设计

你选择了可自主发起任务的 Agent。这意味着它会花掉你的 GPU、占用你的磁盘、 在你睡觉时改变系统状态。所以这一章的重点不是「Agent 能做什么」—— 那部分相对容易——而是它不能做什么、如何被限制、以及出错后如何收拾。

8.3–8.5 回答工程上的三个问题：runtime 是自研还是站在开源框架上、 harness 内核到底由哪几件东西构成、插件怎么封。 结论是自研内核 + 借 dsh/Cordis 的插件范式 + 复用 MCP 协议。

8.1 前提：Agent 只是一个特殊的用户

最重要的架构约束 Agent 没有任何后门。它触达的是与前端完全相同的领域服务—— 同样的鉴权、同样的契约门禁、同样的资源准入、同样的审计日志。 唯一的区别是它的身份是 actor_type=agent， 因而受一套更严格的配额与白名单约束。

措辞上要精确一点：「同一套 API」指的是同一套门禁与同一套领域逻辑，不是同一条 HTTP 传输。 单机部署下 harness 与 API 同进程，工具直接调进程内 service（见 8.10）， 不绕 loopback。真正的不变量是没有特权通道： 所有动作都必须经过 ToolBus 与领域层的校验， 而这个收口点恰好也是前端请求最终落到的地方。

这个约束带来什么

  • Agent 不可能绕过门禁做出人做不到的破坏
  • Agent 的每个动作都天然可审计、可回放、可归因
  • 平台不需要为 Agent 写第二套逻辑，维护成本减半
  • 把 Agent 换成另一个模型、或直接关掉，系统照常运行

Agent 的真实价值定位

它不是「更聪明的研究员」，而是不会累的值班员。 它的优势在于：24 小时盯着队列与曲线、记得住三个月前那次相似的失败、 愿意把 40 个配置一个个跑完并整理成表、 不会因为「差不多了」就跳过检查项。 把判断留给你，把耐心留给它。

明确不指望它做的事

  • 设计新的奖励函数或网络结构
  • 判断某个研究方向是否值得投入
  • 决定真机放行（S0/S1/S2 一律需人工）
  • 解释物理现象的成因（它可以列出可疑项，但结论归你）

8.2 三层架构

为什么规则优先而不是 LLM 优先 「显存不够就减小 num_envs 重试」这种事，用 if 语句写出来是确定的、免费的、瞬时的、可测试的； 交给 LLM 则变成不确定的、要花钱的、有延迟的、难测试的。 LLM 应该只处理那些确实需要判断力的部分。 按经验，日常运维中 80% 的动作可以用规则覆盖， 剧本再覆盖 15%，剩下 5% 才真正需要 LLM——而这 5% 恰恰是它最有价值的地方。

8.3 Runtime 选型：自研内核，借范式，不借地基

先说结论 Harness 内核自研（Python，约 2000 行），插件范式抄 deepseek-harness / Cordis， 协议层复用 MCP 与 OpenAI tool-calling schema，但不把 dsh 作为运行时地基。 理由一句话：agent 循环不是难的部分，护栏、审计、上下文构造才是—— 而后面这些没有任何框架能替我们写。 引入重框架的结果是「难的照样自己写，还多背一层抽象和一条升级跑道」。
方案代表能拿到什么 代价判断
A 纯自研 — 完全贴合领域；零版本风险；调试路径最短 会话循环、流式、schema 校验、上下文压缩都要自己写。实测量级约 1500–2500 行，比想象的小 内核采用
B Python agent 框架 LangGraph · Pydantic-AI · OpenAI Agents SDK 循环、工具 schema、流式、重试、多模型适配现成 抽象形状不匹配：LangGraph 的图状态是为「一次性工作流」设计的， 我们要的是常驻值班员 + 剧本优先；框架的 agent 循环反而要被我们绕开 部分借用
Pydantic-AI 仅作 LLM 客户端与 schema 层
C dsh / Cordis deepseek-harness 成熟的「一切皆插件」范式、DI 与生命周期作用域、Web UI、插件生态 引入 Node 作为第三运行时；工具无法直接访问 Python 领域对象； 官方明示 developer preview 且会有破坏性变更 借范式不借地基
D 协议层复用 MCP · OpenAI tool schema 互操作：我们的工具可被 Cursor / Claude Desktop 直接调用；外部 MCP 工具可接进来 需维护一层 schema 导出，但它由类型签名自动生成（见 8.4） 采用
为什么不直接用 dsh 当地基 ① 它的强项我们一个都不需要。dsh 是编码 agent harness——终端执行、文件编辑、diff、LSP、沙箱。 而我们的 agent 明确没有 shell、没有文件系统、没有任意 HTTP（见本节安全边界）， 它只调那二十来个平台 API。买了一整套厨具只为了拧瓶盖。
② 语言错位的代价是结构性的。我们的工具需要直接访问 Python 领域对象—— 契约校验器、容量估算器、调度器的预算账本。 harness 若在 Node，每个工具都要跨进程 RPC 回 Python： 把本可以是函数调用的东西变成网络调用，只为了用一个插件框架。
③ 地基风险。README 原话是「THERE WILL BE COMPATIBILITY-BREAKING CHANGES」。 对单人维护的项目，把 agent 内核压在一个明示会破坏兼容的 preview 上， 代价会在某个你正忙着调机器人的周一早上兑现。
④ compose 里再加一套构建链。已有 Python + Rust 两套依赖锁与安全更新， 加 Node 就是第三套。单机部署的每一个新运行时都是长期税。
但有四件事值得照抄 ① Everything is a Plugin，连核心能力也是插件。 这对我们不是审美偏好而是刚需——平台的成长路径就是「新训练栈 / 新模型族 / 新本体」， 详见 8.5。
② Cordis 式的 DI + 生命周期作用域。 插件声明依赖哪些服务而不是 import 全局单例；卸载时自动回收它注册过的一切 （路由、定时任务、事件订阅、工具）。这条直接消灭「插件卸下了但定时任务还在跑」这类幽灵 bug。
③ 插件即独立单元、可独立分发。 我们不需要插件市场，但需要「接一个新本体不必改主仓库」。
④ 把 benchmark 与快照测试当一等公民。 dsh 仓库里有 BENCHMARK.md 和整套 snapshot / e2e 配置。 agent 唯一可靠的测试方式就是回放 + 快照断言，见 8.4。

Agent 的 LLM 跑在哪里：一个容易漏的资源冲突

别让 agent 的脑子吃掉训练的卡 如果 agent 的 LLM 用本地 vLLM 起一个 32B 模型，那它常驻占掉一张 4090—— 而我们总共只有四张，还要跑 Isaac 和 π₀。这等于为了「不会累的值班员」永久裁掉四分之一算力。

决定：默认走 API 托管模型（成本以 token 计，不占 GPU）， 预算与 GPU 预算分开记账。本地推理作为可选项，但必须满足两个条件： ① 经容量估算器申报并占用一个正式的资源槽位， 不允许「悄悄常驻」；② 标记为可抢占，优先级低于一切训练任务—— 训练要卡时，agent 先让位。它只是值班员，不是主角。

安全边界：agent 的沙箱就是工具白名单本身

编码 agent 通常需要我们给不给为什么
shell / exec不给 它要做的每件事都已有对应的平台 API。给 shell 等于把前面所有护栏变成装饰—— 能执行任意命令的 agent 的权限矩阵是一张空表
文件读写不给 代码仓库是只读的，产物走 CAS。 需要读日志就用 logs.tail，需要读配置就用 query.*——这些都带审计
任意 HTTP / 浏览不给 出网能力意味着数据外泄路径与提示注入的放大器。 需要的外部资源（HF 权重、镜像）由人发起的入库流程引入
直连数据库 / SQL不给 绕过领域逻辑的写入会破坏血缘与状态机不变量。只读也不给—— 因为 schema 是内部实现，agent 依赖它就等于冻结了我们的重构自由
子 agent 无限派生限制 允许，但深度 ≤2、共享同一份预算与速率账本。防的是「派生出一百个分身各自守规矩， 合起来把机器打满」
这张表的意义 编码 agent 需要沙箱，是因为它的能力集本质上是开放的（任意代码、任意命令）， 只能靠隔离来约束后果。我们的 agent 能力集本质上是封闭的—— 一张二十来行的工具表，每行都经过 ToolBus 的护栏。 封闭能力集不需要沙箱，它自己就是沙箱，而且是可读、可审计、可推理的那种。 这是「agent 只是一个特殊用户」这条前提带来的第二个红利。

8.4 Harness 内核：ToolBus 是唯一收口

为什么「唯一收口」值得当作硬性约束

  • 护栏只写一遍。如果规则引擎能直接调 API 抄近路， 那预算和审计就有了旁路，而旁路一定会在赶时间的那天被用到
  • LLM 挂掉不影响护栏。护栏在 ToolBus 而不在提示词里。 「请不要删除数据」写在 system prompt 里叫许愿，写在 ToolBus 里叫约束
  • 审计天然完备。「agent 昨晚干了什么」＝ 查 ToolBus 的流水， 不存在「有个动作没走审计」的可能
  • 可回放。录下 ToolBus 的输入输出就等于录下 agent 的全部行为

六个内核能力（也就是全部）

  1. Session/Turn 循环：turn 级的 token、工具调用次数、墙钟三重上限；随时可中断， cancel 信号透传到工具执行
  2. 工具注册表：由类型签名生成 schema，见下
  3. 上下文构造器：摘要与引用化，见 8.10 三条原则
  4. ToolBus：上图七道处理
  5. 磁带录制与回放：LLM I/O + 工具 I/O 全量落盘
  6. 流式输出：token、工具状态、审批请求走同一条 SSE 通道到 UI

清单到此为止。凡不在这六项里的，都应该是插件而不是内核。

工具定义的单一真源

# 工具的 schema、权限、限速、文档、MCP 描述符全部由这一处生成
@tool(
    name="job.submit",
    risk=Risk.MEDIUM,
    approval="auto_if",           # 见下方 policy
    rate="6/day",
    budget="gpu_hours",
    dry_run=True,                 # 必须实现，否则注册时报错
    policy="gpus <= 1 and hours <= 6",   # 超出则自动升级为需审批
)
async def submit_job(
    ctx: ToolCtx,
    spec: JobSpec,                    # pydantic 模型 → JSON Schema
    reason: str = Field(..., min_length=10,
        description="为什么要跑这个任务，会出现在审计与审批卡片上"),
) -> JobRef:
    """提交一个任务。提交前必须先调用 capacity.estimate。"""
    # 前置依赖由 ToolBus 校验，不是靠提示词提醒
    ctx.require_prior_call("capacity.estimate", within_turn=True)
    ...

一处声明，五处受益：JSON Schema（喂给 LLM）、 MCP descriptor（导出给 Cursor / Claude Desktop）、 8.6 权限矩阵那张表（由注册表渲染，不再手写）、 审批卡片字段、OpenAPI 文档。

权限表必须由代码生成 8.6 那张权限矩阵如果是手写的 Markdown 表格， 它会在第三次改代码之后开始说谎——而一张说谎的权限表比没有权限表更危险， 因为你会依据它做授权决定。 所以它必须是注册表的渲染结果，并且 CI 里加一条快照测试： 权限表变化必须出现在 diff 里，让改权限这件事无法悄悄发生。
require_prior_call 这个小机制 「提任务前必须先查容量估算器」——写在提示词里，LLM 大概会遵守； 写成 ToolBus 的前置校验，它必须遵守。 凡是能变成机器约束的规范，就不要留在提示词里。 提示词负责倾向，ToolBus 负责不变量。

结果引用化：一个机制同时解决两个问题

# ToolBus 对工具返回值的统一整形
{
  "ref_id": "tr_8f3a21",          // 完整结果存 session store
  "summary": {                       // 只有这部分进入 LLM 上下文
    "n_runs": 14,
    "best": { run: "r_7c21", success_rate: 0.62 },
    "truncated": true,
    "how_to_expand": "query.detail(ref_id, fields=[...])"
  },
  "bytes_full": 1843200,           // 原始 1.8 MB，摘要 < 2 KB
  "cite_as": "[tr_8f3a21#best.success_rate]"
}
同一个 ref 机制既防幻觉又压上下文 防幻觉：agent 输出里的每个数字都必须写成 cite_as 的形式， UI 渲染成可点击引用，点开看原始数据；没有 ref 的数字标灰为「未经核实」 （8.6 已有此约定，这里给出它的实现落点）。
压上下文：1.8 MB 的查询结果只有 2 KB 进入上下文， 需要细节时 agent 自己调 query.detail 展开——按需而非预先。
两件事本来要两套机制，引用化让它们共用一套。 这类「一个机制解决两个问题」的地方，是设计里最值得多花半天的地方。

回放与快照测试：agent 唯一可靠的测试方式

磁带（tape）机制

每个 session 落一份磁带：所有 LLM 请求/响应、所有工具调用/返回、所有护栏判定、时间戳。 磁带既是审计凭据，也是测试夹具。 

# tests/agent/test_playbook_oom.py
async def test_oom_降配重试():
    tape = load_tape("fixtures/oom_isaac_4096.jsonl")
    result = await replay(tape, mode="assert_actions")
    assert result.actions == [
        ("logs.tail",        {"run_id": "r_7c21"}),
        ("capacity.estimate", {"num_envs": 3072}),
        ("job.submit",       {"num_envs": 3072}),
    ]
    assert result.llm_calls == 0      # 这条路径不该用到 LLM
    assert result.budget_delta <= 6.0

mode="assert_actions" 时 LLM 调用从磁带回放而不真的发出去， 所以测试免费、离线、确定。

最有价值的断言是 llm_calls == 0 8.2 说过 80% 的动作应该由规则覆盖。 这句话如果没有测试，会慢慢腐化成「反正 LLM 也能处理」， 于是规则层逐渐空心化，成本和不确定性一起上升。 为每条规则路径断言「零次 LLM 调用」，是守住三层架构的唯一办法。
场景夹具集 维护一组带标注答案的场景磁带：OOM、标定过期、指标不显著却想扫参、 磁盘将满、契约不匹配、被要求做禁止动作（越权拒绝也要测）。 新增护栏或改提示词时全量回放。 这就是 dsh 仓库里 BENCHMARK.md 那件事在我们场景下的对应物。

8.5 插件封装：一个插件装下「一个栈的全部知识」

这是抄 dsh 范式带来的真实收益，而且和 agent 无关 今天要接入一个新训练栈（比如换掉 RLInf，或加一个新的 VLA 家族），需要改六个地方： 适配器、容量公式、日志/指标解析、契约校验规则、前端面板、agent 工具。 它们散落在三个目录里，漏掉任何一处的表现都是「跑起来了但某个环节静默不对」。

插件契约要解决的就是这件事：把这六样东西放进同一个包、同一个 manifest、同一次评审。 「Everything is a Plugin」对我们的意义不是可扩展性， 而是让「接入一个新栈」从一件需要记忆清单的事变成一件有模板的事。
贡献点类型例子不做插件化的后果
adaptersJobSpec → 命令行/Hydra rlinf · isaaclab_rslrl 主仓库里堆 if/elif，每加一个栈动一次核心代码
estimators容量公式 provider Isaac 的 c_env 标定曲线；FSDP 的 B(optimizer) 表 公式与适配器分家，改了优化器却忘了改估算 → OOM
validators契约门禁扩展 G3 的 io_signature 反查按栈有差异 新栈绕过门禁而没人发现
metrics日志与指标解析 tfevents · SwanLab · stdout 正则 曲线画不出来，或指标名对不齐导致跨栈对比失真
toolsagent 工具 rlinf.suggest_placement agent 对新栈无知，只能给通用建议
knowledge提示片段 + 失败签名 Isaac 常见崩溃签名与修复步骤 失败诊断退化为「贴日志给 LLM」
ui前端远程模块（ESM） RLInf 的 component_placement 可视化 新栈的专有参数只能以 JSON 原文展示
playbooks剧本定义 该栈专有的诊断流程 剧本集合无法随栈演进

插件形态与 Cordis 式的生命周期

# plugins/eb_plugin_rlinf/__init__.py
MANIFEST = PluginManifest(
    name="rlinf",
    version="0.3.1",
    api_version="1",              # 启动时校验，不兼容则拒载
    requires=["scheduler", "capacity", "cas"],   # 声明式依赖注入
    contributes=["adapters", "estimators", "metrics",
                 "tools", "knowledge", "ui"],
)

def setup(ctx: Context) -> None:
    # ctx 是作用域句柄：它注册的一切都挂在这个作用域上
    ctx.adapter(RlinfAdapter())
    ctx.estimator("train.rlft", rlinf_fsdp_formula)
    ctx.metrics_parser("tfevents", TfEventsParser())
    ctx.tool(suggest_placement)              # 自动进权限矩阵
    ctx.knowledge(Path("knowledge/"))
    ctx.ui_panel("placement", "dist/placement.mjs")
    ctx.on("run.failed", diagnose_rlinf_failure)

    # 不需要写 teardown：作用域销毁时以上全部自动注销

「不需要写 teardown」是这套设计的核心收益。 手工卸载一定会漏——漏掉的定时任务和事件订阅会在插件卸下之后继续跑， 而且极难定位。作用域化注册让「注册」和「回收」在结构上对称， 漏不掉是因为它不由人来记。

插件是同进程 Python，即完全信任 我们不做插件沙箱与进程隔离。理由：单机单人，插件全部由我自己或明确信任的来源提供， 隔离的成本（IPC、序列化、调试困难）远超收益。 诚实地承认这一点，比假装有安全边界更好—— 假的边界会让人误以为可以随便装第三方插件。

但仍要有三条工程纪律：① 插件不得直连数据库，只能通过注入的 service； ② 单个插件加载失败必须降级（禁用该插件并在 UI 报警）， 不能拖垮整个 API 进程；③ api_version 不匹配直接拒载， 不做「试试看能不能跑」。
热重载：开发要，生产不要 dev 用 watchfiles 监听插件目录重载作用域—— 改一行适配器不用重启整个 FastAPI，这在调适配器时能省下大量时间。 生产环境的「重载」就是 docker compose restart api： 单机部署下服务重启是秒级的，为它做热更新是纯粹的复杂度支出。
插件契约的隐性好处 即使永远只有我一个人写插件、永远不做插件市场， 这套契约依然值得——因为它强制核心与领域知识解耦。 「把自己的代码也当插件写」是最有效的防腐手段： 当核心不得不通过公开契约来使用领域逻辑时，它就没法悄悄长出耦合。

8.6 工具集与权限矩阵

② 修改契约：契约是判断对错的基准，改基准等于取消检查。
③ 门禁豁免：如果 Agent 能豁免门禁，那么门禁对 Agent 就不存在。

预算是硬约束 Agent 每周 60 GPU·h 配额（与 05 章 的调度面板一致）。用完即停，不接受「再借一点」。 预算独立于你自己的用量，这样即使 Agent 疯了，也只能糟蹋掉四分之一的算力， 而不是把你的活挤掉。

8.7 剧本：Agent 的主要工作方式

剧本是写死的多步流程，Agent 负责触发与填参，而不是即兴发挥。 这让自主行为变得可预测——你能提前知道它会做什么。

剧本触发步骤产出与价值
训练失败诊断 run 进入 failed ① 取退出码与日志尾部 → ② 匹配已知失败模式库 → ③ 若 OOM 则算出可行的 num_envs 并重试 → ④ 若为环境问题则贴出对应修复步骤 → ⑤ 若无法归类则调 LLM 分析并附上相似历史案例 失败不再需要你先去看日志。覆盖率高的部分完全不需要 LLM
超参扫描 人工发起或例行 ① 按声明的搜索空间生成配置 → ② 分批提交（并发受预算约束）→ ③ 早停明显更差的分支 → ④ 汇总成对比表与 Pareto 图 → ⑤ 给出推荐与理由 你只需看最后一张表。早停能省下大量无谓的 GPU·h
夜间队列填充 每晚 23:00 ① 检查空闲 GPU → ② 从待办池取低优先级任务 → ③ 以可抢占方式提交 → ④ 早上 8:00 前主动腾出资源 把闲置算力变成结果。抢占式提交保证不影响白天的工作
上机前检查 策略包创建 ① 跑完 G1–G5 → ② 跑 sim2sim 一致性 → ③ 核对标定新鲜度与固件 → ④ 检查维护记录是否有未处理项 → ⑤ 生成检查清单交给人 把琐碎但关键的核对做完。最后按钮仍由人按
数据缺口分析 评估报告产出 ① 按维度拆解失败样本 → ② 与训练集分布对比 → ③ 找出覆盖薄弱的组合 → ④ 生成「建议采集 N 条 X 类样本」的清单 把「模型不行」翻译成「缺什么数据」。针对 35 场景的现状特别有用
资源与存储巡检 每天 07:00 ① 统计磁盘趋势 → ② 列出可回收候选（附证据：无血缘引用、超期、有更优版本）→ ③ 等人确认后执行 防止磁盘写满导致训练崩溃。删除动作永不自动执行
日报 每天 09:00 ① 汇总 24 h 内的 run/评估/放行 → ② 标出异常与趋势 → ③ 列出待你决策的事项 → ④ 一段自然语言总结 这是给同事看你产出的主要载体，也是你自己的进度回顾

8.9 失效模式与对策

自主 Agent 一定会出问题。区别在于问题是否被限制在可承受范围内、 以及你能否快速发现并纠正。

失效模式具体表现对策残余风险
幻觉数字「成功率提升了 12%」——实际没查过工具返回值带 ref，输出中的数字必须引用；无 ref 的标灰仍可能对趋势描述夸大（「显著改善」），这类定性词无法机械校验
无限循环失败→重试→失败，反复烧 GPU同一 job 自动重试上限 2 次；同一剧本 24 h 内触发上限；预算硬顶低。预算是最后防线
误判归因把 seed 波动当成方法改进并据此扫参强制在结论中带置信区间；对比页自动标注「差异不显著」中。它可能仍在不显著的差异上浪费算力
资源挤占夜间提交的任务占满 GPU，早上你没法工作Agent 任务默认可抢占；固定时段（08:00–20:00）自动降优先级低
盲目乐观报告只说好消息，异常一笔带过日报模板强制包含「异常与风险」段，为空时需说明依据中。模板能强制结构，但不能强制诚实
过度打扰每个小波动都发通知，最后你把通知全关了通知分级；同类事件合并；每天通知数上限低但需调优
审批疲劳连续批准后失去审查意识高风险审批要求填写一句理由；三条永久禁止线不给审批入口中。这是人的问题，工具只能减轻
LLM 服务不可用API 挂了或超预算规则与剧本层完全不依赖 LLM，可独立运行；仅失去开放式对话能力很低——这是三层架构的直接收益
一个关键的产品判断 Agent 的自主级别应该可随时下调，并且下调不需要改配置文件重启服务—— UI 上一个按钮，立刻从「可自主发起」变成「仅给建议」。 因为信任是逐步建立的：刚开始你会想看着它做每一步， 几周之后确认它靠得住了，再放开。把这个滑块交给用户，比替用户决定要好。

8.10 实现要点

Agent 不需要独立进程

在单机场景下，harness 就是 FastAPI 应用里的一个模块 + 一组 APScheduler 定时任务。 它订阅 Redis Streams 的事件、按 cron 触发剧本、通过进程内 service 调用领域逻辑 （不走 loopback HTTP——护栏在 ToolBus 而不在 HTTP 层， 绕一圈网络只会让调试变难、延迟变高）。 不要为它做微服务——那只会增加部署复杂度而没有任何收益。

唯一的例外是 MCP 桥：对外暴露工具时它是一个独立端点， 因为外部客户端（Cursor / Claude Desktop）本来就在进程外。

经验库的朴素实现

「记得住三个月前的相似失败」听起来需要向量数据库，实际上不需要。 失败模式的判别特征是结构化的：退出码、异常类名、日志中的关键行、 JobKind、镜像 digest。用一张 PG 表存 (signature, cause, fix, occurrences, last_seen)， signature 由这些字段规范化后哈希——精确匹配就能覆盖大部分情况。 只有匹配不上时才需要 LLM 去做模糊关联。

上下文构造是主要工程量

LLM 的效果几乎完全取决于喂给它什么。三条实践原则：

  • 给聚合而非原始：曲线传 200 个降采样点，不传 6000 个 iter
  • 给结构而非文本：传 JSON 事实表，不传拼接好的自然语言段落
  • 给差异而非全量：对比两个 run 时只传参数 diff 与指标 diff

这三条能把上下文压到十分之一，同时提高准确率—— 因为噪音本身就是幻觉的来源。

审计日志的字段 每条 Agent 动作记录：actor_type=agent、 trigger（事件 / cron / 人工指令）、 playbook_id 与步号、tool 与参数、 guardrail_result（通过 / 降级 / 拦截）、 budget_delta、llm_call_id（若有）、结果与耗时。 有了这些字段，「Agent 昨晚干了什么」是一次 SQL 查询，而不是一场考古。
