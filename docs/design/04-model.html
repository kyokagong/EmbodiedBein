04 · Models & Assets

模型与本体资产管理

这个模块管两类东西：会学习的部分（模型权重与其谱系）和不会学习但必须一致的部分 （URDF/MJCF/USD 资产、标定数据）。后者常被忽略，但三种格式之间的静默漂移 会让「仿真里好好的策略上机就抽」——这是具身研发最典型的时间黑洞。

4.1 两类模型，两套约束

平台要同时管理量级差六个数量级的两类模型。把它们塞进同一套流程会让小模型被拖累、大模型被约束不足， 因此在注册表里用 family 区分并应用不同的默认策略。

A 类 低层运控策略

代表RSL-RL PPO 的 Actor-Critic MLP
参数量10⁵ 量级
输入obs 75 / 45 / 85 维向量
输出act 22 / 12 维关节位置
训练单卡，瓶颈在 Isaac 仿真而非模型
产出model_*.pt → policy.onnx / policy.pt
上机直接上机，ONNX Runtime 推理

关键治理点：checkpoint 数量爆炸（每 100 iter 存一次 × 6000 iter = 60 个）与 导出物与契约的严格一致。

B 类 视觉-语言-动作模型

代表π₀ / π₀.₅、OpenVLA(-OFT)、GR00T、LingBotVLA
参数量3B – 7B
输入state[10] + camera[224,224,3] + 语言指令
输出action chunk（含 horizon）
训练多卡 FSDP，受 24 GB 显存严格制约
产出global_step_*/actor/（HF 格式目录）
上机需推理服务，延迟是硬约束

关键治理点：显存画像（提交前就知道放不放得下）、基座权重来源与许可、 推理延迟是否满足控制周期。

4.2 注册表与谱系

Model 是逻辑身份（一条研究线索），ModelVersion 是不可变的具体权重。 谱系记录「从哪个基座、用哪批数据、经哪次训练得来」，这是复现与影响分析的基础。

4.3 模型卡

模型卡是 ModelVersion 的必填元数据。缺少任一必填项则无法注册——这是刻意的摩擦，用来防止半年后没人知道某个权重是怎么来的。

字段必填说明
contract_id是本体契约。没有契约的权重不允许进注册表，只能作为裸 Artifact 存在
family / arch是rsl_rl_mlp / openpi / openvla / gr00t / lingbotvla …；与 RLinf 的 model_type 对齐
base_model条件微调模型必填。指向平台内 ModelVersion 或外部 URI（HF repo + revision）
produced_by是产出它的 Run。外部导入的模型此处为 imported 并必填来源 URL
training_data是DatasetVersion 列表 + 各自权重。外部模型填 unknown 并标风险
license / license_flags是权重许可 + 从训练数据继承的传染标记（如 nc_tainted）
io_signature是自动填充：从权重文件实际读出的输入输出形状与 dtype，用于 G3 校验
mem_profile自动容量画像，见 4.4。含 confidence（measured/analytic）与配置指纹；每次运行后由 eb-collector 用 NVML 峰值回填，不需要人工填写
latency_profile条件上机前必填：单次推理 p50/p95 延迟（在目标硬件上实测）
metrics_summary自动关联评估报告的关键指标快照
intended_use / limitations建议一两句话说明适用场景与已知失效模式。写给三个月后的自己和同事
tags否baseline / candidate / deployed / deprecated

4.4 容量估算器（4×24 GB 的硬约束）

方法论借鉴 llmfit llmfit（Rust，MIT）做的是「检测本机硬件 → 对每个模型算出能不能跑、跑多快 → 并且每个估算都附带它的假设与验证命令」。 它本身面向 LLM 推理，不覆盖我们最吃紧的训练与 Isaac 仿真，但它有三个做法值得直接搬过来： ① 估算必须自带出处（estimate basis），不能是一个孤零零的数字； ② 硬件探测是一等产物（llmfit doctor），而不是把「4×24 GB」硬编码在文档里； ③ 实测覆盖估算——一旦在本机量过，就用实测值替换公式值。 下面把这三条落成平台的 MemoryEstimator。

4.4.1 三层估算：实测 > 解析 > 目录

层来源置信度适用安全系数
L1 实测 本机历史 Run 的 NVML 峰值，按配置指纹索引 measured n≥3 跑过的配置。这是绝大多数情况——同一套配置我们会反复跑几十次 p99 × 1.10
L2 解析 按栈的显存公式（见 4.4.2），输入来自 JobSpec 与权重文件头 analytic 新配置、改了 batch/卡数/优化器的配置 上界 × 1.25
L3 目录 外部目录（llmfit / HF config.json）提供的骨干参数量与量化选项 estimated 只知道模型名、还没下载权重时的粗筛 上界 × 1.4，且只用于警告，不用于放行
为什么这个顺序比「更准的公式」更重要 显存公式无论多精细，都躲不开 allocator 碎片、cuDNN workspace、NCCL 缓冲这些实现细节， 误差 10–20% 很正常。而我们的工作负载种类少、重复率极高—— 就那么几个模型、几个 num_envs 档位。所以只要坚持把每次实测写回去， 几周之后 L1 就能覆盖 90% 的提交，公式退化为「新配置的第一次猜测」。 用积累代替精确，比用精确代替积累现实得多。

4.4.2 按栈的解析公式

A · 梯度下降训练（RLinf / FSDP）

# 每卡静态占用（N 卡分片）
V_static = P_train × B(optimizer) / N
         + P_frozen × 2 / N          # 冻结部分仍需 bf16 权重

# B(optimizer)：每可训练参数的字节数
AdamW fp32 states + fp32 master  →  16
AdamW bf16 states                →  8
8-bit AdamW (bitsandbytes)       →  8
SGD momentum fp32                →  10

# 每卡总占用
V_peak = V_static
       + V_act(batch, seq, layers, ckpt)   # 需实测标定
       + V_ctx                             # CUDA ctx + NCCL ≈ 1.2 GB
       + 碎片余量 ≈ 8%

P_train 与 P_frozen 由平台读权重文件头得到（与 4.5 契约反查共用同一套读取逻辑），不依赖人工填写； B(optimizer) 从 Hydra 配置里解析。 V_act 是唯一必须靠实测标定的项——它随实现变化太大，硬算不划算。

B · Isaac Lab 仿真（RSL-RL）

V_peak = V_isaac_base                # Isaac Sim 运行时，3–6 GB
       + n_envs × c_env              # c_env 必须标定
       + V_render(cameras, 分辨率)    # 无相机时为 0
       + V_policy                    # MLP，可忽略（< 50 MB）

注意这里模型大小几乎无关——显存被物理求解器和碰撞几何占满。 c_env 取决于刚体数、碰撞体复杂度与接触对数量， 无法从 URDF 静态推算，只能按（契约 × 任务）标定一次然后线性外推。 好消息是外推在 n_envs 上相当准，因为它就是逐 env 复制的。

C · 推理服务（vLLM / SGLang / ONNX）

V_peak = P × bytes(dtype)            # bf16 → 2
       + V_kv(seq, batch, layers)    # VLA 场景很小
       + V_ctx + 碎片

这一层正好是 llmfit 的主场：它的记忆模型就是为「权重 + KV cache + 上下文」设计的， 还带量化档位选择。VLA 推理的上下文极短（一帧观测 + 一句指令）， KV cache 通常不到 1 GB，所以估算相当可靠。 可直接复用 llmfit

D · 无 GPU 任务

MuJoCo sim2sim（ONNX Runtime CPU）、数据扫描、校验、报告渲染、资产一致性检查—— V_peak = 0。调度器把它们当作可与任意 GPU 任务并发的自由任务， 这也是把 sim2sim 设为强制门禁的隐含理由：它不跟任何人抢卡。

硬件不硬编码：ebd doctor 「4×24 GB」应当是探测结果而不是文档常量。 ebd doctor 输出一份 HostProfile： 每卡型号 / 总显存 / 当前占用 / 驱动与 CUDA 版本 / 计算能力 / 是否有 /dev/dri / NVLink 拓扑 / 主机内存与 shm 上限。 它在服务启动时与每次调度决策前刷新，也是诊断包的一部分。 好处：换一张卡、加一条内存、驱动升级后，所有准入判断自动跟着变， 不需要去改任何配置或文档。

4.4.3 按公式复核：原先的手写估算有两处过于乐观

把 4.4.2 的公式套到我们真正要跑的模型上（N=卡数， V_act 取梯度检查点开启时的经验区间 3–6 GB，V_ctx=1.2 GB，碎片 8%）， 结论与原先手写的表有两行不一致，而且都是偏乐观的方向：

配置可训练参数优化器卡数 静态/卡峰值/卡结论依据
RSL-RL · biped 12 DOF · 4096 envs0.1 MPPO1 —12–18充裕 measured n=14 · p99 15.8 GB
RSL-RL · humanoid 22 DOF · 4096 envs0.1 MPPO1 —14–20充裕 measured n=6 · p99 19.1 GB
π₀.₅ · 全参 SFT3.3 BAdamW fp32（16 B/p）2 26.4> 30不可行 analytic 3.3e9×16/2 = 26.4 GB，静态就已超 24
π₀.₅ · 全参 SFT3.3 BAdamW fp324 13.218.8–22.0可行但紧 analytic (13.2+V_act+1.2)×1.08。需占满 4 卡，期间跑不了别的
π₀.₅ · 全参 SFT3.3 B8-bit AdamW（8 B/p）2 13.218.8–22.0推荐 analytic 峰值与上一行相同，但换优化器等于省下两张卡
OpenVLA-7B · 全参 SFT7.5 BAdamW fp32（16 B/p）4 30.0> 34不可行 analytic 原表写「22–24 GB 高风险」是错的，实际连静态都放不下
OpenVLA-7B · LoRA r=32~40 MAdamW + 冻结基座2 7.813.0–16.2可行 analytic 冻结基座 2×7.5e9/2=7.5 GB + LoRA 可忽略
GR00T N1.x · SFT~3 B待定4 12.017.5–20.7待验证 estimated 变体与冻结策略未确认
π₀.₅ · RLFT（actor + rollout 分置）3.3 B8-bit AdamW4 13.2（actor 2 卡）18.8–22.0很紧 analytic rollout 2 卡各 ~8 GB；component_placement: actor 0-1, rollout 2-3
π₀.₅ · 推理服务3.3 Bbf16 推理1 6.68–10充裕 analytic KV cache < 1 GB（上下文极短）
MuJoCo sim2sim—ONNX CPU0 —0无 GPU 可与任何任务并发
这两行修正的实际意义 ① OpenVLA-7B 全参微调在 4×24 GB 上做不了，不是「很紧」而是「放不下」—— 仅优化器状态就要 120 GB。要用它只能走 LoRA，或者 8-bit 优化器 + 4 卡（约 19–21 GB/卡，仍很紧）。 ② π₀.₅ 全参 SFT 用常规 AdamW 需要 4 张卡，不是 2 张； 但把优化器换成 8-bit 就能压回 2 张卡——省下的两张卡够并行跑一个 Isaac 训练。

这正是「估算自带出处」的价值：原表那两个数字看着合理， 但因为没写出「按什么算的」，错了也没人能发现。 而这两个错误如果不是现在发现，代价是某天跑了 8 小时之后 OOM。 以上均为解析值，需在首次实跑后用 NVML 峰值校准

}

四个字段各自的作用

  • confidence 决定安全系数，也决定 UI 上显示什么徽标。 「未校准」必须显式可见，否则人会把估算当实测信任
  • basis.inputs 让每个数字都能追到来源。 看到不对劲的估算时，能立刻定位是哪个输入错了—— 比如发现 P_train 是 7.5e9 而你以为在跑 LoRA，那就是配置没生效
  • verify 给出一条可复制的命令。 --probe-memory 只跑 20 步就退出，几分钟内把估算变实测
  • alternatives 是最实用的一项：被拒绝时直接告诉你改什么能过， 而不是让你自己猜。每条都附带代价（慢多少 / 效果可能如何）
--probe-memory 值得单独实现 它是 llmfit 的 bench 在我们场景下的对应物： 用真实镜像、真实配置起容器，跑到显存达到稳态（通常 20–50 步）就退出。 成本几分钟，换来一个 measured 数据点。 对于要跑 20 小时的任务，先花 3 分钟探一次显存是极划算的交易， 应该做成提交表单里的默认建议动作。

4.4.5 校准闭环

配置指纹怎么取

fp = hash(
  job_kind,
  contract_id,        # 影响 Isaac 的 c_env
  model_version_id,   # 或 base_model + 冻结策略
  optimizer_kind,
  n_gpus,
  micro_batch, grad_ckpt,
  n_envs,             # Isaac
  image_digest,       # 版本变了显存也会变
  host_profile.gpu_model
)

指纹刻意不含 seed、学习率、总步数、experiment 名——这些不影响显存。 含 image_digest 是因为框架升级经常改变显存行为， 老实测值不该套用到新镜像上。

线性外推是允许的 在 n_envs 与 micro_batch 这两个维度上， 若已有 ≥2 个实测点，估算器可以线性外推并标为 interpolated（安全系数取 1.15）。 这两个旋钮正是日常调得最多的，能外推就省掉大量重复探测。 其余维度（卡数、优化器、模型）不外推——它们的关系不是线性的。
整机组合的可行性（按修正后的公式）单位 GB/卡 · 上限 24

最后一列 OpenVLA 全参已溢出（实际需 >34 GB/卡），图上只能画到顶格—— UI 上这种情况必须显示为红色的「no_fit」而不是「满格」， 否则容易被误读成「刚好放得下」。

准入规则（由估算器驱动）

  1. measured：p99 × 1.10 与当前空闲显存比较
  2. analytic：上界 × 1.25，UI 标 未校准，并建议先跑 --probe-memory
  3. estimated（仅目录数据）：不放行，只给警告与建议
  4. 余量 < 1.5 GB 直接拒绝，附 alternatives 清单
  5. 该指纹曾 OOM → 拒绝，除非显式 --force 并写理由
  6. Isaac 任务要求 /dev/dri 且整卡独占，不参与共享
  7. 推理服务（serve.policy）是唯一允许共卡的类型： 两个 ≤10 GB 的服务可同卡，但不与训练共卡——训练的峰值波动会把它挤死

目标始终是把「跑到第 8 小时 OOM」变成「提交时就被拦住，并且告诉你改什么能过」。

要不要真的引入 llmfit 这个依赖 建议：借鉴方法论，选择性复用，不放在关键路径上。
值得用的：硬件探测（doctor）的实现参考； 推理场景（4.4.2-C）的记忆模型与量化档位选择； 它的 Rust core 可作为 crate 引入，与我们的数据面同语言；MIT 许可无障碍。
不能指望的：它的目录里没有 π₀ / GR00T 这类 VLA 模型（可用自定义模型机制补，但要自己填参数）； 它完全不涉及训练时的优化器状态与激活，而这正是我们最吃紧的部分； 它更不知道 Isaac Sim 的 n_envs 会吃掉十几 GB—— 而 Isaac 恰好占了我们大部分 GPU 小时。
结论：把 MemoryEstimator 设计成带 provider 接口的组件， llmfit 作为「推理 + 骨干参数」这一路的可选 provider。 即使完全不引入它，上面的三层结构与凭据格式也照样成立—— 真正的收益是那套方法论，不是那个二进制。

4.5 契约反查（G3 / G4 实现）

平台不相信配置文件里写的维度，而是直接从权重文件读。这样即使有人手改了 YAML 也逃不过。 

# backend/eb/models/introspect.py
def read_io_signature(path: Path) -> IOSignature:
    """从产物本身反查输入输出形状，不读任何配置文件。"""
    if path.suffix == ".onnx":
        m = onnx.load(path, load_external_data=False)
        ins  = [(i.name, _shape(i)) for i in m.graph.input]
        outs = [(o.name, _shape(o)) for o in m.graph.output]
        return IOSignature("onnx", ins, outs, opset=m.opset_import[0].version)

    if path.suffix == ".pt":
        # TorchScript：从 graph 的 input types 推断；失败则用 validation_observations.pt 试跑一次
        mod = torch.jit.load(path, map_location="cpu")
        try:
            return _from_jit_graph(mod)
        except Inconclusive:
            obs = torch.load(path.with_name("validation_observations.pt"))
            out = mod(obs[:1])
            return IOSignature("torchscript", [("obs", tuple(obs.shape[1:]))],
                                             [("act", tuple(out.shape[1:]))])

    if path.is_dir():   # HF 格式（VLA）：读 config.json + 权重 shape 抽样
        return _from_hf_dir(path)

def check_g3(sig: IOSignature, ctr: Contract) -> CheckResult:
    v = []
    if sig.inputs[0][1][-1] != ctr.observation.dim:
        v.append(Violation("onnx.input[0].dim", ctr.observation.dim, sig.inputs[0][1][-1],
                           hint="观测维度不符——最常见原因是导出时 --task 与训练不一致"))
    if sig.outputs[0][1][-1] != ctr.action.total_dim:
        v.append(...)
    return CheckResult(not v, v)
Berkeley 导出物给了我们额外的礼物 play.py 会同时导出 validation_observations.pt。这个文件让平台可以做比维度检查更强的验证： 用同一批观测分别喂给 policy.pt 与 policy.onnx，比对输出是否逐元素一致 （容差 1e-5）。这能抓住 ONNX 导出过程中的算子行为差异——一个真实存在且极难排查的问题类别。 平台把这项检查加入 G4，命名为 export_consistency。

4.7 本体资产一致性

这是一个真实存在的漂移风险 同一台机器人在仓库里有四种描述：URDF（真机/IK）、MJCF（MuJoCo sim2sim）、 USD（Isaac 训练）、SCAD/STL（几何）。它们由 export_onshape_to_urdf.py / export_onshape_to_mjcf.py 从 Onshape 分别导出。 如果某次只重新导出了 URDF 而忘了 MJCF，sim2sim 门禁就会用错误的模型去验证策略， 结论完全不可信，而且极难察觉。
资产用途一致性校验项失败症状
*.urdfPinocchio IK、真机运动学、teleop 三方交叉比对：
· 关节数与名称集合相同
· 关节顺序与契约 joint_order 一致
· 位置/速度/力矩限位数值一致（容差 1e-6）
· 连杆质量与惯量一致
· 父子拓扑同构 		IK 解算出的关节角映射到错误的电机
*.xml (MJCF)sim2sim 回归验证门禁通过但真机失败（门禁失去意义）
*.usdIsaac Lab 训练训练出的策略与真机动力学不匹配
meshes/*.stl碰撞与渲染碰撞体与视觉不一致 → 数量校验 + 文件哈希仿真里穿模或误判碰撞
scad/*.scad可参数化几何（脚掌等）版本记录，不参与运动学校验—

上例中 knee_l 的速度限位在 URDF 与 MJCF 里不一致——这正是那种「跑一年都不会有人发现， 但会让 sim2sim 结论系统性偏乐观」的问题。校验器把它标为 blocking。

资产版本策略

  • 资产按 本体版本（不是 git commit）打版：bhl-hw-v1.2
  • 一个资产版本 = 四种格式 + 网格文件的整体快照，有统一内容哈希
  • Run 记录使用的资产版本；换资产 = 换实验条件，不允许静默替换
  • Onshape 导出脚本包装为 asset.export Job，产出即入 CAS，避免「本地导出后忘记提交」
  • 资产版本与 EmbodimentContract 双向引用：契约声明兼容的资产版本范围

4.8 标定管理

标定是什么

calibrate_joints.py 产出 calibration.yaml，记录每个关节的零位偏移。 这是仿真世界与物理世界之间唯一的对齐参数，错了机器人就以错误的姿态起始。

平台如何管

  • 绑定到具体 RobotInstance（不是机型）
  • 记录标定时间、操作者、环境温度（可选）
  • 设有效期：默认 30 天，或「任何机械维修后立即失效」
  • 与前一次标定做 diff，偏移突变超阈值时告警（通常意味着装配变动或编码器打滑）

G5 卡口用它做什么

  • 标定不存在 → 阻断部署
  • 标定已过期 → 阻断，提示重新标定
  • 标定关节数 ≠ 契约 dof → 阻断
  • 标定所属机器人 ≠ 部署目标 → 阻断（防止把 A 机的标定用到 B 机）

4.9 模型许可与外部权重

需要你逐个核对的事 平台可以强制「必须填许可字段」，但无法替你判断某个开源 VLA 权重的商用条款。 因此 ModelCard 的 license 字段在首次注册外部基座时必须人工填写并留下依据链接， 平台之后才会沿血缘自动传播。当前你可能用到的基座包括 π₀/π₀.₅、OpenVLA、OpenVLA-OFT、GR00T—— 这四个的许可条款各不相同，建议在 M1 阶段一次性核对清楚并录入。

checkpoint 保留策略（省磁盘的关键）

策略适用保留
top_kA 类 RL 训练按指标最优 5 个 + 最后 1 个
last_and_bestB 类 SFT/RLFT最新 1 + 最优 2
every_n需要中间态分析每 N 步 1 个
all调试全留，强制设 TTL

优化器状态（往往是权重的 2 倍大）默认只保留最新一个，30 天后 GC； 已发布或被引用的 checkpoint 自动 pinned，永不回收。 以 A 类训练为例：60 个 checkpoint 降到 6 个，直接省下 90% 的模型存储。

与上游的复用

  • scripts/rsl_rl/play.py --export_only → export.policy Job 的执行体
  • --deployment_config → 生成部署 YAML，平台接管其输出路径避免污染仓库
  • checkpoints/policy_*.onnx（仓库内预置参考策略）→ 作为「基线模型」导入注册表， 用于对比新策略是否真的更好
  • RLinf toolkits/ 的 checkpoint 转换脚本 → model.convert Job
一个容易忽略的价值点 仓库里已有多个版本的预置 ONNX 策略（checkpoints/policy_*.onnx）。 把它们导入注册表并跑一遍统一的评估套件，你就立刻拥有了一条基线—— 之后每个新策略都能回答「比原来的好多少」，而不是只能说「成功率 0.71」。 这是平台上线第一周就能产出的价值。
