# 07 · 七轮深度反思与边界审查

为了保证再审方案在真实生产与科研环境（4×RTX 4090 单机、真实 BHL 代码仓、真实 RLinf 框架）中严密无懈可击，我们进行了 **7 轮多角度极限推演与反思**。

---

## 第 1 轮 · 4 卡硬件与多任务并发碰撞反思

> **疑问**：当用户在 4×4090 机器上同时跑两个 2 卡任务（Job A 占 GPU 0,1，Job B 占 GPU 2,3）时，系统是否会发生隐蔽碰撞？

### 深度剖析：
1. **Ray 集群端口冲突**：RLinf 启动命令中包含 `ray start --head --port 6390`。若两个容器都使用固定端口 6390 且使用 host 网络，后起的任务会直接因端口占用而失败崩溃。
2. **共享内存 (`/dev/shm`) 耗尽**：两个 Isaac Lab 并行仿真任务同时申请 32GB 共享内存，可能触发系统级 OOM-Killer 导致机器死机。
3. **显存碎片化与竞争**：Ray 默认可能探测到全量 4 张卡并尝试初始化未分配的 GPU。

### 终版对策：
- **容器物理隔离**：每个任务容器均通过 Docker `--gpus '"device=0,1"'` 严格限定 GPU 物理可见性，容器内部无论如何只能看见分配给它的卡（在容器内映射为 cuda:0, cuda:1）。
- **动态 Ray Head 端口**：基于 Job ID 动态分配 Ray 端口（`6390 + offset`）。
- **显存与内存约束**：容器强制配置 `--shm-size=32gb`，调度器增加内存总配额预检，若宿主机总剩余内存不足则进入排队。

## 第 2 轮 · 代码仓只读保护与产物写死权限反思

> **疑问**：为什么必须强制代码仓只读？如果训练容器由 Docker root 启动，宿主机的开发者后续如何管理产物？

### 深度剖析：
1. **写脏代码仓灾难**：若将 `/data/kk/Berkeley-Humanoid-Lite` 挂为 `rw`，RLinf 的某些第三方库可能会在代码目录下自动创建 `__pycache__`、`.pytest_cache`、甚至在源码根目录写入 `runs/` 日志，导致 git 脏工作区，破坏实验可复现性。
2. **Root 文件权限锁死**：Docker 容器默认以 `root` 权限运行，在 `/var/lib/eb/runs/<id>/output` 写入的 `.pt` 权重文件的所有者为 `root:root`。宿主机用户 `kk` 在终端通过 `rm`、`mv` 或代码调试这些权重时会遭遇 `Permission Denied`。

### 终版对策：
- **强制只读挂载**：外部代码仓挂载参数固定为 `:ro`。
- **用户身份透传**：`ebd` 启动容器时透传宿主 UID/GID（`--user $(id -u):$(id -g)`）或统一设置容器内部 `umask 0002`，确保宿主机普通用户可随意支配所有输出产物。

## 第 3 轮 · 3D 资产与多 URDF 切换渲染反思

> **疑问**：BHL 仓内有 4 份 URDF，网格文件分散在不同子目录，Three.js 在浏览器端如何确保 100% 渲染成功且不卡顿？

### 深度剖析：
1. **相对路径解析失效**：URDF 中的 `<mesh filename="../meshes/stl/foo.stl"/>` 在浏览器端无法直接通过标准 URL 加载。
2. **USD 格式兼容性**：USD 资产在 Web 端的解析成本极高（需要几十 MB 的 WebAssembly wasm 运行时），容易导致页面卡死。
3. **多变体丢失**：若只扫描第一个找到的 URDF，用户无法查看 12DoF 双足形态或 10DoF 固定手部形态。

### 终版对策：
- **安全资产代理**：通过 `/api/v1/embodiments/:id/assets/*` 提供受控的静态资源映射。
- **全 URDF 变体识别**：扫描所有 `*.urdf`，构建变体列表供前端一键下拉切换。
- **3D 体验降级兜底**：主攻 URDF + STL/OBJ/DAE 渲染；若目录仅有 USD/MJCF，则展示代码与关节树结构，并在 3D 画布中优雅提示「当前检测到 USD/MJCF 资产，推荐在 Isaac Sim 中查看」，绝不抛出未捕获前端异常。

## 第 4 轮 · 大数据集下载容错与断点续传反思

> **疑问**：从 Hugging Face 或 HTTP 下载 44GB 数据集时，若网络在 90% 时中断，是否会导致前功尽弃？

### 深度剖析：
1. **重复下载带宽浪费**：几十 GB 数据如果无断点续传，一次网络抖动会导致用户重新等待数小时。
2. **下载死锁与僵尸进程**：若用户刷新页面或关闭浏览器，FastAPI 中的同步下载逻辑可能失去监控导致后台僵尸下载。
3. **磁盘容量被撑爆**：未做预检导致磁盘写到 100%，引发宿主机操作系统级崩溃。

### 终版对策：
- **预检磁盘配额**：通过 `statvfs` 进行容量预检，剩余容量不足时拒绝启动下载。
- **异步 Worker 架构**：下载任务由后台 Worker 独立管理，状态持久化到数据库。
- **断点续传与原子写入**：
  - Hugging Face 基于官方 API 的 chunked transfer 自动续传。
  - HTTP 基于 Range 请求头写入临时文件 `.tmp`，下载并校验完成后原子化（`os.rename`）移动至目标目录。

## 第 5 轮 · RLinf 与 Hydra Overrides 配置容错反思

> **疑问**：Hydra 配置体系极其严格，若用户在表单的高级 Overrides 里写错一个字母（如把 `max_epochs` 写成 `max_epoch`），会导致什么后果？

### 深度剖析：
- Hydra 在遇到未知配置键时会抛出 `HydraException / KeyError` 并直接 `exit(1)`。容器启动 2 秒后立即退出并处于 `failed` 状态。如果平台仅显示抽象的「任务失败」，用户会误以为是驱动、镜像或系统 BUG。

### 终版对策：
- **前端输入校验与高亮提示**：在输入 overrides 时，前端对照已加载的模板 key 进行粗校验。
- **秒级错误精准捕获**：当容器在启动 10 秒内退出时，`ebd` 立即提取最后 30 行终端日志，通过正则精准匹配 `Could not override 'xxx'` 或 `KeyError`，在任务详情页以醒目的黄色横幅提示：「参数覆盖配置有误，请核对 Hydra 键名」。
- **一键复制复现命令**：提供一键复制 `docker run ...` 等价命令，方便用户直接在终端排查。

## 6. 第 6 轮 · 模型 Checkpoint 识别与血缘闭环反思

> **疑问**：训练可能每 10 个 epoch 保存一个 checkpoint，一次训练输出 20 个 `.pt` 文件。若全部自动登记，模型列表是否会泛滥成灾？

### 深度剖析：
- 如果全部强制自动登记，模型列表会被海量中间权重（`step_10.pt`, `step_20.pt`...）淹没，用户难以找到真正可用的最终模型；如果只支持手动登记，用户又必须等几个小时训练结束后守在电脑前点击登记。

### 终版对策（采纳用户确认的最优解）：
- **双模并存**：
  1. **手动自由挑选**：训练详情页动态展示 Checkpoint 列表，用户可随时点击任何一个有价值的 step 进行登记。
  2. **自动登记 Latest 选项**：在新建训练表单中提供开关「训练成功后自动登记最新 checkpoint」。开启后，任务以退出码 0 结束时，系统自动解析并登记最新的 `best_model.pt` 或最大 step 的权重。

## 第 7 轮 · 极简主义与产品认知负荷反思

> **疑问**：历史设计中的评估（EvalSuite）、排行榜（Leaderboard）、真机部署（Bundle/Robot）、Agent（ToolBus）是否会以某种形式悄悄渗透回来增加认知负担？

### 深度剖析：
- 很多系统在重构时，往往会在侧边栏或二级页面保留「评估报告」、「门禁状态」等只读入口，导致使用者依然要分心理解「为什么我的任务没过 G3 门禁」。

### 终版裁决：
- **彻底移出主视野**：
  - 导航栏严格固定为 6 项（总览 / 本体 / 数据 / 环境 / 训练 / 模型）。
  - 不再将 G1~G5 门禁作为训练提交或模型保存的前置阻断条件。
  - 历史代码保留在底层模块中作为内部能力沉睡，绝不主动在前端 UI 和主操作流中弹窗阻断。
  - 使用者的心智模型始终保持极致纯粹：**选本体 → 看镜像 → 挂数据/基座 → 填参数 → 开训 → 看指标日志 → 存模型**。
