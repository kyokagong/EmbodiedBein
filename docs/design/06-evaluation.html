06 · Evaluation

评估体系与可视化

「成功率 0.71」这句话几乎没有信息量——在哪个套件上、几个 seed、置信区间多宽、 比基线好多少、失败的那 29% 长什么样、在 MuJoCo 里还成不成立？ 这一章的目标是让每个结论都自带这些上下文，并且能被门禁自动判定。

6.1 五层指标体系

指标按「离最终目标的距离」分层。层次越低越易得、越即时；层次越高越接近真实价值、越昂贵。 训练时看 L0/L1，决策时看 L2，上机前看 L3，上机后看 L4。

层关注具体指标来源用途
L0
过程		 训练是否健康 reward mean/std、surrogate loss、value loss、entropy、KL、grad norm、lr、SPS、GPU util、显存峰值 tfevents（每 iter） 判断「要不要现在停掉重来」；不能作为结论
L1
行为		 机器人在仿真里做了什么 episode 长度、终止原因分布（超时/倾倒/触限/自碰撞）、timeout_rate、failure_rate、 速度跟踪误差、臂关节跟踪 RMSE（WBC）、安全违规计数、动作饱和率、动作抖动（一阶差分能量） tfevents + play.py --metrics_output 解释 L0 的变化「为什么」；运控任务的主要判据
L2
任务		 任务到底成没成 success_rate（分任务/分物体/分指令模板）、子目标完成率、完成步数、 OOD 泛化（换措辞 / 换物体 / 换初始位）、成功率的 Wilson 置信区间 EvalSuite 运行结果 决策依据；进入门禁与排行榜
L3
跨域		 换个物理引擎还成立吗 轨迹发散步数、动作序列 L2 偏差、观测项分布漂移（逐维）、接触/步态相位相似度、 三域指标差（Isaac vs MuJoCo vs Real） sim2sim + 真机遥测 上机前最后一道理性防线；见 6.4
L4
部署		 真机上跑得住吗 控制环周期抖动（jitter p99）、策略推理延迟、CAN 错误率与丢帧、IMU 丢包、 电机温度与电流峰值、E-stop 触发次数、单次运行时长（MTBF 代理） 真机遥测 见 07 · 遥测
一个常见误区 L0 的 reward 上升不等于任务变好。奖励函数是代理目标，被钻空子很常见 （典型症状：reward 涨但倾倒率不降，说明策略学会了在倒下前刷分）。 平台的对策是在同一屏并列 L0 与 L1（见 05 · 训练可视化）， 并在门禁里只用 L1/L2 做判据，绝不用 reward 当发布条件。

6.2 评估套件与 seed 注册表

评估必须是可重复且可比较的。这要求把「测什么」冻结成 EvalSuite， 并用 seed 注册表保证不同模型面对完全相同的初始条件。 

api_version: eb/v1
kind: EvalSuite
metadata: { name: suite_reach_push_v2 }
spec:
  contract_id: ec_bhl_fixedhand_10dof_v1
  frozen: true                 # 冻结后不可修改，只能出 v3

  splits:
    - name: id                     # in-distribution
      scenarios: dsv_…4M2#slice=val
      episodes: 64
      seeds: seed_registry_v2#id     # 固定 64 个 seed，跨模型完全一致
    - name: ood_instruction
      scenarios: dsv_…4M2#slice=val
      episodes: 32
      mutate: { instruction: paraphrase_set_a }   # "reach" → "move toward" 等
    - name: ood_object
      episodes: 32
      mutate: { object_color: [green, yellow], object_scale: [0.85, 1.15] }
    - name: ood_init
      episodes: 32
      mutate: { init_pose_noise: 0.06 }

  metrics_contract:            # 声明必须产出哪些指标，缺失即评估失败
    required: [success_rate, steps_to_success, failure_reason]
    optional: [subgoal_rate, action_smoothness]

  artifacts:
    video: { record: failures_and_sample, max: 24 }   # 全录会爆盘
    trajectory: { record: all, downsample: 1 }

  aggregation:
    by: [split, task_family, object_family]
    ci: wilson_95              # 成功率是二项分布，用 Wilson 区间而非 ±std
seed 注册表为什么必须独立 如果每次评估随机取 seed，两个模型的成功率差 3% 可能纯粹是运气。 固定 seed 集合后，差异可归因到模型本身，还能做逐 episode 配对比较 （同一个 seed 下 A 成功 B 失败 → 直接调出这一对视频看差别）。 仓库里的 --seed-registry 参数已经体现了这个思路，平台把它制度化。
样本量与置信区间 64 个 episode 的成功率若为 0.80，Wilson 95% 区间约为 [0.68, 0.88]。 也就是说 0.80 与 0.75 在 64 样本下无法区分。 平台在所有成功率旁强制显示区间与样本量，并在对比页对「区间重叠」的结论标注 差异不显著。 这会让人不舒服，但比自欺欺人好。若要区分 5% 的差距，需要约 250+ episode。

四类 OOD 是刻意设计的

  • 换措辞：测语言理解是否泛化，还是只记住了模板
  • 换物体：测视觉泛化（当前数据只有红圆柱与蓝方块，泛化风险极高）
  • 换初始位：测策略鲁棒性
  • 三者同时变：真实场景的近似

以当前数据规模（35 场景 / 14 个指令模板），OOD 掉分会很严重， 但这恰恰是有价值的信息——它告诉你该补什么数据。

6.3 跨域一致性诊断（L3）

为什么这值得单独设计 你的链路是 Isaac 训练 → ONNX 导出 → MuJoCo 验证 → UDP/CAN 上机。 每一次跨域都可能引入偏差：物理引擎不同、资产参数漂移、观测噪声特性不同、 时序与延迟不同。目前这些偏差只能靠上机后「感觉不对」来发现。 L3 的目标是把它变成一张可读的表：告诉你偏差有多大、来自哪一维。

三个诊断量

① 轨迹发散步数

同一策略、同一初始状态、同一 seed，在 Isaac 与 MuJoCo 里并行推进， 记录状态差 ‖s_A(t) − s_B(t)‖ 首次超过阈值的步数 t*。

怎么读：t* 越大越一致。若 t* < 10 步（即 0.4 s @25 Hz）， 说明两个模型的动力学根本不同，sim2sim 门禁的结论不可信， 应先去查资产一致性。

② 观测项分布漂移（最有用）

对契约里每一个观测 term 分别统计三域下的均值与方差，计算标准化差异 （如 Wasserstein 距离或简单的 |Δμ|/σ）。

怎么读：这张热力图直接指出 sim2real gap 的来源维度。 比如若 projected_gravity 在真机上偏移最大，问题在 IMU 标定或滤波； 若 joint_vel_rel 偏差大，问题在电机模型或编码器差分方式。 这比「策略在真机上不行」有用一万倍。

③ 动作序列偏差

同一观测序列喂给策略应得到同一动作（策略是确定的）， 所以动作偏差完全来自观测偏差。逐步计算 ‖a_A(t) − a_B(t)‖ 与其累积。

怎么读：把动作偏差与观测偏差做相关性分析，可定位「哪一维观测的扰动被策略放大了」， 即策略对该维度过度敏感——这是需要在训练中加噪声域随机化的信号。

6.4 回归门禁

Gate 是一组断言。它的价值不只在「拦住坏策略」，更在防止悄悄退步—— 没有基线比较的评估，很容易在追求某个指标时把另一个搞坏了。 

api_version: eb/v1
kind: Gate
metadata: { name: gate_reach_push_release }
spec:
  subject: eval_report
  assertions:
    # ── 绝对门槛（来自仓库既有约定）
    - name: reach_success
      expr: 'm["success_rate", split="id", task="reach"] >= 0.80'
      severity: blocking
    - name: push_success
      expr: 'm["success_rate", split="id", task="push"] >= 0.60'
      severity: blocking

    # ── 统计可靠性
    - name: enough_samples
      expr: 'm["n_episodes"] >= 64'
      severity: blocking
    - name: ci_not_too_wide
      expr: 'm["success_rate_ci_width"] <= 0.20'
      severity: warning

    # ── 防回归（与已发布基线比）
    - name: no_regression_vs_released
      expr: 'm["success_rate"] >= baseline("rel_reach_v0.2.0").m["success_rate"] - 0.03'
      severity: blocking
    - name: ood_not_collapsed
      expr: 'm["success_rate", split="ood_instruction"] >= 0.5 * m["success_rate", split="id"]'
      severity: warning

    # ── 安全与可执行性
    - name: no_limit_violation
      expr: 'm["safety.joint_limit_violations"] == 0'
      severity: blocking
    - name: latency_ok
      expr: 'm["inference_p95_ms"] <= 0.7 * contract.control.policy_period_ms'
      severity: blocking

    # ── 跨域一致性（L3）
    - name: sim2sim_consistent
      expr: 'm["divergence_step"] >= 100'
      severity: blocking
    - name: obs_drift_bounded
      expr: 'max(m["obs_drift"].values()) <= 0.6'
      severity: warning

  on_fail:
    blocking: stop_pipeline + notify + open_diagnosis
    warning:  notify

门禁 DSL 的设计取舍

  • 不用完整 Python eval：安全风险且难审计。用受限表达式（仅比较、算术、少量内置函数）
  • m[...] 支持按 split / task / object 维度取值，这样一条断言能覆盖分组
  • baseline(release_id) 是关键函数：把「防回归」变成一等能力
  • contract.* 可访问契约字段，让「延迟 ≤ 70% 控制周期」这类断言自动适配不同频率的本体
  • 两级严重度：blocking 停流水线，warning 只通知——避免门禁太严导致大家绕过它
门禁必须可解释 失败时不能只说「gate failed」。UI 显示每条断言的 表达式、期望值、实际值、涉及的样本，并给出一键跳转到失败样本视频的入口。 门禁的可信度取决于人能不能快速验证它的判断是对的。
关于既有阈值 reach ≥ 0.80 与 push ≥ 0.60 来自仓库里已有的 CLOSED_LOOP_GATES 约定，平台直接沿用以保持一致。 但要注意：这两个数字在 64 样本下的置信区间宽达 ±0.10， 所以「刚好卡在 0.80」的策略实际上不可靠。建议把发布门槛与统计显著性绑定， 即要求「区间下界 ≥ 门槛」而非「点估计 ≥ 门槛」。

6.8 实现要点

评估结果的存储形态

评估报告是三层结构，各层存储不同：

层内容存储
聚合分组成功率、CI、门禁结果PG jsonb（可查询、可排序）
逐 episode每条的 seed / 成功 / 步数 / 失败原因Parquet in CAS（列式，便于筛选与配对比较）
媒体失败视频、轨迹CAS + 代理片段

逐 episode 用 Parquet 而非 PG 行的原因：一次 256 episode × 多个套件 × 几十个模型 会产生十万级行，而查询模式是「按 seed 配对 join」——列式格式在这个模式下快得多， 且可以直接被 pandas/DuckDB 读取做临时分析。

视频不能全录 一个 256 episode 的评估若全录视频，按每段 2 MB 计就是 512 MB， 几十次评估就把盘吃光。策略：默认只录失败样本 + 少量成功样本抽样 （record: failures_and_sample, max: 24）。 若需要全录，必须显式指定并自动设 7 天 TTL。

与上游评估脚本的对接

上游产出平台处理
play.py --metrics_outputJSON：timeout_rate / failure_rate / safety.* / metrics.* / arm_tracking直接解析为 L1 指标
eval_rlinf_openpi.pyJSON：success_rate解析为 L2；需补齐逐 episode 明细
eval_lingbot_v2.py closed-loop报告 + 失败视频目录L2 + 媒体认领；沿用其 gate 阈值
validate_dataset.py数据集校验归入数据模块，见 03
play_mujoco.py仿真回放（当前无结构化输出）需小幅扩展以输出轨迹与 L3 指标

唯一需要改上游的地方：play_mujoco.py 目前是可视化用途， 要支持 L3 诊断需让它能无头运行并导出状态/动作序列（约几十行改动）。 这是整个设计里对上游侵入最大的一处，且是必要的——没有它就没有跨域一致性。

指标计算在哪里做 基础指标由脚本自己算（平台不重算，避免两套实现不一致）。 平台只做三件事：聚合（跨 episode / 跨 seed）、统计推断（CI、显著性）、门禁判定。 这个边界让平台不需要理解任务语义，也就不会因为任务变化而需要改代码。
