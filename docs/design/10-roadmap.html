10 · Roadmap

实施路线与风险

前九章描述了一个完整的系统；11 补画面， 12 把契约替换为本体环境。 这一章处理一个更现实的问题： 在只有你一个人、算力有限的前提下，按什么顺序做，才能每一步都立刻有用。 以及同样重要的：哪些地方我判断不了，需要你来定。

10.1 排序原则

① 每个里程碑独立可用

不做「先搭三个月基础设施再看到东西」。 M0 结束时就应该有一个能打开、能看到你现有资产的页面。 能用的半成品 > 完美的未完成品。

② 先记录，后控制

「把已有的东西纳管并可视化」比「通过平台下发任务」简单得多， 风险也低得多，但价值不低——因为它立刻解决了「产出看不见」的问题。 所以只读能力全部前置。

③ Agent 放最后

Agent 是所有 API 的消费者。API 不稳定时做 Agent， 等于同时调试两个不确定的东西。 而且没有 Agent 平台也完全能用，它是增益而非基础。

10.2 六个里程碑

M0
2 周

骨架 + 只读纳管　最先出价值

做什么：docker-compose.yml 与两个 Dockerfile（从第一天就用 compose 起，不要先在宿主裸跑再迁移）；FastAPI 骨架 + Postgres schema + Vue 骨架 + 静态托管； EmbodimentContract 实体与四个契约实例落库； 扫描并注册现有资产——checkpoints/ 下的 ONNX 策略、 logs/ 下的历史 tfevents、berkeley_ego_data 的目录清单。

为什么先做这个：不需要 Docker、不需要调度、不需要 Rust， 纯读取现有文件系统。但做完之后你立刻有一个可分享的链接， 上面有你所有历史策略与训练曲线。这是整个项目里投入产出比最高的两周。

验收：在一台干净机器上 git clone && make up 后浏览器能打开；能看到 ≥6 个历史策略、≥10 条历史训练曲线、4 个契约； 每个策略能显示其 I/O 签名并与契约比对出结论；Showcase 链接可发给同事打开。

M1
3 周

任务下发闭环（Isaac / RSL-RL）

做什么：Rust ebd runner（Docker 生命周期 + 日志采集）； Isaac Lab 适配器；工作区隔离（git worktree 快照 + overlay 挂载）； eb-tsdb 最简版 + 指标采集；Run 详情页实时曲线与日志； 单机调度器（4 GPU 准入 + 队列），准入依赖 ebd doctor + 容量估算器的解析层 （L2 公式 + 估算凭据；实测校准留到 M2 自然积累）。

难点：Isaac Sim 容器的 GPU 渲染参数、镜像体积、 写路径隔离（logs/ 与 outputs/ 必须落到 overlay）。 建议先手工跑通一次容器命令，再把它固化成适配器—— 不要一开始就写抽象。

验收：从 UI 提交一次 train.rl，能看到实时曲线与日志， 产物自动认领入库；上游仓库工作树保持干净（git status 无变化）； 同一 JobSpec 提交两次能复现（五元组一致）；4 GPU 满载时第 5 个任务正确排队。

M2
3 周

评估、门禁与对比

做什么：EvalSuite + seed 注册表；play.py --metrics_output 与既有评估脚本的结果解析；门禁 DSL 与判定引擎；Run 对比页（参数 diff + 显著性标注）； 评估报告页与失败视频墙；排行榜与基线。

为什么排在数据前面：你已经有能跑的策略与评估脚本， 所以评估能力立刻可用；而数据模块（尤其是重定向）不确定性大、 且当前数据量小，收益兑现慢。先把能立刻用上的能力做完。

验收：对同一策略在固定 seed 集上跑两次，成功率完全一致； 门禁能拦下一个已知有问题的策略并给出具体断言； 对比页能正确标注「差异不显著」；仓库预置的 6 个策略排出第一张基线榜。

M3
4 周

数据模块 + RLinf 适配器　不确定性最高

做什么：Rust ebd scanner（格式嗅探 + 完整性校验）； 六层数据模型与版本化；数据漏斗审计视图；Episode 预览器； RLinf 适配器（Hydra 覆盖 + Ray 端口隔离 + 组件放置）；VLA 训练与评估打通。

风险最集中的一段：RLinf 的镜像与依赖较重，Ray 在容器内的行为需要实测； 人类 ego 数据到机器人轨迹的重定向管线可能做不出可用结果。 建议把重定向单独作为可选子项，主线只做「注册 + 校验 + 漏斗审计 + 预览」。

验收：能提交一次 RLinf 的 SFT 任务并看到指标； 数据漏斗页能展示 155k → 35 的每一级与拒绝原因； Episode 预览器能同步播放视频与动作曲线；数据集版本可复现（同版本哈希一致）。

M4
3 周

部署流水线与遥测

做什么：策略包规范与打包/签名；导出自检（含 ONNX vs PyTorch 数值比对）； sim2sim 门禁与跨域一致性诊断（需小改 play_mujoco.py）； 资产一致性校验；分级放行流程与 Fleet 台账； 端侧 eb-robot-agent 最简版（接包 + 上报）。

验收：从一个 checkpoint 一键产出已签名策略包； 故意把 MJCF 限位改错，sim2sim 门禁能拦下并指出具体关节； 真机跑一次并在平台看到 jitter/温度/事件；能一键回滚且回滚不依赖网络。

M5
3 周

Agent

做什么：harness 内核（ToolBus 七道处理、工具注册表、磁带录制/回放）； 护栏（白名单 / 预算 / 速率 / 审批）；规则引擎与 7 个剧本； LLM 接入与上下文构造；控制台 UI；审计视图；MCP 导出。

建议的内部顺序：先做只读 + 日报（零风险，立刻有用）， 再做规则引擎 + 失败诊断（高价值，无需 LLM）， 最后才开放自主提交任务。每一步观察一周再放开下一步。

验收：Agent 输出中的每个数字都可点击溯源； 故意让它尝试禁止动作（改契约 / 放行真机），必须被拦截并留审计； 预算耗尽后自动降级为只读；关掉 LLM 服务后规则与剧本仍正常工作； 场景磁带全量回放通过，且规则路径断言 llm_calls == 0； 权限矩阵由注册表生成，快照测试能拦住未声明的权限变更。

关于工期 合计约 18 周，这是「一个人专职、且不遇到大坑」的乐观估计。 实际情况下 M1 与 M3 的容器相关问题很容易各多花一到两周。 如果时间紧张，M0+M1+M2（8 周）就已经构成一个有实用价值的系统—— 能纳管、能下发、能评估、能分享。后三个里程碑可以按需推进。

几个结构上的决定

  • domain/ 保持纯净：不 import 任何 IO 库。这样状态机与契约校验逻辑可以被单元测试直接覆盖，不需要起数据库。
  • adapters/ 一个文件一个栈：新增训练栈时只加一个文件 + 一组快照测试，不动核心。
  • Rust 是 workspace 而非独立仓：单机场景下版本同步的价值大于解耦的价值。
  • robot-agent 单独目录：它部署在另一台机器上，生命周期与平台不同。
  • web/dist 由前端构建写入：不进 git，打包时生成（make build）。

10.4 工程实践：几个容易被跳过但会反复咬人的细节

最小 CI（单人项目也值得）

不需要完整流水线，四个检查就够，全部能在几分钟内跑完：

  1. 类型与静态检查Python ruff + mypy；Rust clippy；前端 vue-tsc
  2. 适配器快照测试最重要的一项：JobSpec → 命令行的输出与基线比对，上游改参数名时立刻失败
  3. domain 层单元测试状态机迁移、契约校验、门禁 DSL 求值。无需数据库
  4. 迁移可回滚检查alembic upgrade head && downgrade -1，防止写出不可逆迁移

刻意不做：端到端测试（需要 GPU 与大镜像，成本远超收益）。 真正的端到端验证靠每个里程碑的验收清单人工跑一次。

单用户模式下的最小鉴权

入口机制说明
Web UI会话 Cookie（HttpOnly, SameSite=Lax）单账号 + 密码；密码哈希存 PG
CLI / 脚本API Key（Authorization: Bearer）可撤销，仅显示一次
Agent内部 API Key，actor_type=agent受工具白名单与配额约束
ShowcaseURL 中的长随机 token仅读一份快照 JSON；可设过期与吊销
robot-agent设备 Key（按 robot_id 签发）只能上报自己的遥测、拉自己的包
免鉴权路由仅 /healthz 与 /showcase/<token>其余全部要求身份

这套东西约 200 行代码，不做 RBAC、不做多租户、不做 OAuth。 但把「谁做的」记进审计日志的能力从第一天就有， 这样将来加人时不需要回溯改数据模型。

遗留资产纳管（M0 的实际难点）

「扫描现有目录并注册」听起来简单，真正麻烦的是建立稳定身份：

  • 身份用内容哈希而非路径：policy.onnx 在多个 run 目录里可能是同一份， 按 sha256 去重后只存一份，路径作为「发现位置」记录
  • 时间来自文件而非导入时刻：用 mtime 与 tfevents 首个事件的时间戳还原历史顺序， 否则所有历史 run 都会显示为「今天创建」
  • 缺失字段显式标为 unknown：历史 run 没有 image digest 与 config hash， 不要伪造，标 provenance: partial，并在 UI 上与完整记录区分
  • 导入可重入：再扫一次不产生重复实体（幂等键 = 内容哈希 + kind）
  • 契约推断而非假设：从 ONNX 的 I/O 维度反查最匹配的契约，匹配不上就标「待人工归属」

最后一条很关键：宁可留一批「待归属」的历史策略，也不要错误绑定契约—— 错误的绑定会让后续所有门禁结论失效。

恢复演练与告警渠道

  • RPO ≈ 24 h / RTO ≈ 1 h：每日 pg_dump，最坏丢一天元数据； 恢复 = 建库 + 恢复 dump + ebctl reindex 重建与文件系统的一致性
  • 每季度演练一次：从备份在临时库恢复并跑一次一致性检查。 没演练过的备份等于没有备份
  • reconcile 优先信任文件：PG 与文件系统冲突时，以 CAS 与 runs/<id>/spec.json 为准重建索引，因为它们是 append-only 的
  • 告警渠道：默认 Webhook（可接飞书/Slack/邮件网关）； 分三级——需立刻处理（磁盘满、GPU 掉卡）、需当天关注（门禁失败、趋势异常）、 仅记录。同类事件 30 min 内合并，每日总量上限，防止告警疲劳
端侧协议的定稿时机 robot-agent 与平台之间的接口（拉包、上报遥测、心跳、回滚） 应在 M4 开始时先写成一页 OpenAPI 定义再动手， 因为它跨两个进程、两台机器、两种语言，事后改代价最高。 接口面故意做得很小：GET /bundles/next、 POST /telemetry:batch、POST /events、GET /policy/active—— 四个端点足够，不要预留「将来可能有用」的能力。

10.5 风险登记册

风险概率影响 缓解措施预警信号
Isaac Sim 容器 GPU 渲染跑不通中高 M1 第一周就手工验证容器命令；保留「宿主直跑 + 平台仅记录」的退路容器内 --headless 报显示设备错误
RLinf 的 Ray 在容器内异常中中高 显式指定 Ray 端口（6390）与 --num-gpus；共享内存 --shm-size 调大；单节点模式优先Ray head 启动超时或端口冲突
4×24 GB 显存跑不动目标 VLA 模型已确认高 已按公式复核（4.4.3）：OpenVLA-7B 全参微调在本机不可行，必须 LoRA；π₀ 全参需 4 卡或 8-bit 优化器。缓解手段固化为容量估算器的准入规则与降配建议，而非依赖人工记忆不再是「风险」而是已知约束；监控点转为估算器的 analytic 命中率与 OOM 次数
数据量不足导致 VLA 无法泛化高中高 这是已经发生的事实（35 场景）；平台的作用是把缺口量化并指导采集，而非解决它OOD 成功率持续低于 id 的 50%
人类 ego 重定向做不出可用轨迹中高中 列为 M3 可选子项，不阻塞主线；主线走脚本专家采集IK 可行率低或轨迹在仿真中不可执行
磁盘写满导致训练中断中高中 配额 + 分级存储 + 每日巡检剧本；准入时预估产物体积；视频默认不全录磁盘使用率 > 85%
上游仓库变动导致适配器失效中中 固定 code_ref 与镜像 digest；适配器快照测试；升级作为显式动作快照测试失败或参数名不识别
submodule 缺失导致运行失败中低 工作区准备阶段显式校验 submodule 完整性，缺失则提交前即失败资产或低层控制目录为空
许可合规问题（Ego4D 等非商用）中中高 许可标签沿血缘传播；受限数据训出的模型自动打标并禁止标记为可商用出现无许可标签的数据集版本
Agent 烧掉算力或产生噪音中中 预算硬顶 + 白名单 + 可抢占 + 一键降级为只读预算周中即耗尽；通知量激增
平台本身成为负担（维护成本超过收益）中高 刻意不引入 K8s/Kafka 等重组件；每个里程碑独立可用，可随时停在任一阶段你开始绕过平台直接跑脚本
单人维护（bus factor = 1）高中 文档即本套设计；ADR 记录决策原因；避免聪明但难懂的实现—
最后两条风险最值得警惕 「平台成为负担」的预警信号写的是「你开始绕过平台直接跑脚本」—— 这是最诚实也最有用的指标。如果某天你觉得「用平台提交太麻烦，我直接 python train.py」， 那说明平台在那个环节的设计失败了，应该去简化它而不是要求自己遵守流程。 工具服务于人，不是反过来。

10.6 整体验收标准

下面每一条都是可执行的检验，不是主观判断。全部通过即认为平台达成设计目标。

可复现性

  • 任取一个 90 天前的 run，能拿到完整五元组并重新提交，结果指标在容差内一致
  • 任取一个模型版本，能回答「用了哪些数据、哪段代码、哪个镜像」
  • 上游仓库工作树在任何时刻 git status 都是干净的

正确性门禁

  • 人为制造维度不匹配（改契约 obs_dim），G1/G4 必须在提交时拦下
  • 人为制造 URDF/MJCF 限位不一致，资产校验必须报出具体关节
  • 人为让标定过期，真机放行必须被拒
  • 门禁失败时必须显示涉及的断言、期望值与实际值

资源治理

  • 4 GPU 满载时新任务正确排队，不出现 OOM 崩溃
  • Agent 预算耗尽后无法再提交训练任务
  • 磁盘超过阈值时提交被拒并提示可回收清单

协作与可见性

  • Showcase 链接能被没有账号的同事打开并理解项目现状
  • 任意视图能通过复制 URL 分享，对方看到相同内容
  • Agent 的所有动作与人的动作在同一时间线可见
  • 日报能自动生成且包含「异常与风险」段

效率（相对现状的改善）

  • 提交一次训练：从「改配置 + 记参数 + 起容器」到表单 3 分钟内完成
  • 诊断一次失败：从「翻日志目录」到详情页直接看到归类结论
  • 对比两次实验：从「手工对齐 TensorBoard」到勾选两项点对比
  • 向同事说明进展：从「口头 + 截图」到发一个链接
不作为验收标准的东西 代码行数、页面数量、功能覆盖率、技术先进性。 这些都容易刷高但与实际价值无关。 唯一真正的标准是：三个月后你还在用它，而不是绕过它。
