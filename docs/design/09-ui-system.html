09 · UI System

UI 体系与协作

这一章面向三类读者：你（每天用它干活）、同事（想知道你做到哪了）、 未来的实现者（要照着这个搭前端）。 因此内容分成两部分：先把三类视角的信息架构定清楚，再给出可直接落地的设计系统与工程约定。

9.1 三类视角，两套界面

视角核心问题需要的界面设计要点
你
操作者		 现在该做什么？刚才那个为什么失败？这两个配置哪个好？ 完整工作台：数据/模型/训练/评估/部署/Agent 六大区 + 队列 + 命令面板 信息密度优先、键盘可达、深链可分享、状态在 URL 里
同事
观察者		 这个项目进展如何？现在能做到什么程度？有视频吗？ Showcase 只读页：里程碑时间线 + 最新成果 + 演示视频 + 关键指标趋势 解释性优先、无需登录（或只需链接）、不暴露内部细节与失败噪音
Agent
程序		 系统当前状态是什么？我能做什么？ 无界面，走 REST；但其行为必须在 UI 中完全可见 Agent 的动作与人的动作在同一时间线上呈现，不分栏隐藏
为什么 Showcase 要单独做一套而不是「给同事一个只读账号」 只读账号看到的还是你的工作台——满屏的失败 run、队列、报错、 半成品配置。同事看了只会得到「一团乱」的印象，而不是「进展不错」。 Showcase 是主动策展的结果：你决定展示什么、配上一句人话解释。 它把「让同事看到产出」这个诉求从「给权限」变成「讲故事」， 而这两件事的效果完全不同。

9.5 设计系统

模块语义色

六大模块各有固定色，全站一致：徽标、图表主色、导航高亮、血缘图节点都用它。 这样看一眼颜色就知道在哪个域。

数据 模型 训练 评估 部署 Agent 基础设施

状态色（跨全站唯一语义）

运行中　成功 / 通过　 警告 / 待确认　失败 / 阻断　 排队　空闲 / 未开始

关键约定：绿色只表示「通过了检查」，不表示「数值高」。 这避免出现「倾倒率是绿色」这种荒谬情况—— 高倾倒率必须是红的，即使它是个「上升的数字」。

排版与密度

正文15px / 1.75系统无衬线
数值与 ID等宽字体所有数字右对齐、定宽
表格行高32px（紧凑 26px）列表页默认紧凑
主色调深色 #070e14长时间看曲线不刺眼

数字必须等宽且右对齐。这是个小细节，但当你在表格里比较 0.821 和 0.61 时，对齐能让差异一眼可见。

图表规范

场景图型约定
训练曲线折线默认 EMA 0.9 平滑 + 原始半透明；多 seed 显示 ±std 带
终止原因堆叠面积/柱比例而非绝对值；颜色固定绑定原因
成功率矩阵热力图红绿色阶固定 0–1，不自适应（否则无法跨报告对比）
成本 vs 效果散点 + 前沿被支配点降低不透明度
资源占用甘特 / 条形时间轴统一为本地时区
数据流转漏斗每级标注绝对数与留存率
血缘 / DAG节点图节点色 = 模块色；边方向恒为左→右

最重要的一条：同一个 run 在全站任何图表里都是同一个颜色。 颜色由 run_id 哈希决定并缓存。这样跨页面看图时不需要每次重新对照图例。

y 轴不要默认从 0 开始，但要标注 reward 从 18.4 涨到 18.7 时，从 0 起的 y 轴让曲线看起来是直线； 自适应轴又会把噪声放大成「重大突破」。 折中：自适应 + 在轴上明确标注范围 + 提供一键切回 0 基线。 这类小决定累积起来决定了图表是帮人理解还是误导人。

# FastAPI 侧一行挂载

# 注意：需在所有 /api 路由注册之后挂载，否则会吞掉 API 路径
# 且需处理 SPA 回退：未匹配路径返回 index.html

# ── 构建发生在镜像里，不在宿主上 ──────────────────────────
# deploy/api.Dockerfile 第一阶段：
FROM node:20-alpine AS web
COPY frontend/package*.json ./
RUN npm ci
COPY frontend/ ./
RUN npm run build                       # → /app/dist
# ...最后阶段：
COPY --from=web /app/dist ./web/dist   # 前端随 api 镜像一起发布
前端不是独立部署单元 它没有自己的容器、没有自己的端口、也不经 Nginx—— npm run build 在 api 镜像构建时执行，产物直接躺在 api 镜像里。 部署时只有 docker compose up -d 一条命令（见 01.8）。
推论：改一行前端代码需要重建 api 镜像（约 1–2 min）， 所以开发期一定要用 make dev-web 的 Vite 热更新， 把 /api 与 /ws 代理到 compose 里跑着的 :8000—— 前端热更新与后端容器化并不冲突，这是最舒服的开发姿势。

性能预算

首屏可交互< 1.5 s
主 bundle（gzip）< 400 KB
曲线渲染 10k 点< 120 ms
列表 5k 行滚动60 fps
日志 100k 行虚拟滚动，内存 < 60 MB
WS 重连指数退避，上限 30 s

three.js（3D 资产查看器）与 Vue Flow（血缘图）必须懒加载， 否则主 bundle 预算立刻超标。

曲线降采样在后端做 一次训练 6000 iter × 31 个指标 = 18 万点。全传给浏览器再抽稀是浪费。 TSDB 查询接口直接支持 ?points=200， 服务端按时间桶做 min/max/avg 聚合返回—— 既保留了尖峰（min/max）又控制了体积。这是 Rust 侧 eb-tsdb 存在的主要理由之一。
URL 即状态 筛选条件、选中的 run、图表的 x 范围、展开的标签页——全部编码进 URL query。 这样「把这个视图发给同事」等于「复制地址栏」， 也让浏览器前进/后退符合直觉。 这是协作类工具最划算的一个设计投入。
空状态与错误状态要认真做 平台刚上线时所有列表都是空的。空状态如果只显示「暂无数据」， 用户不知道下一步该干什么。每个空列表都应该给出 一句解释 + 一个具体动作按钮（如「注册第一个数据集」）。 同理，错误提示必须包含「发生了什么 / 可能原因 / 我能做什么」三段。

9.7 可用性细节

键盘优先

  • ⌘K 命令面板：跳转任意实体、提交任务、问 Agent
  • j/k 列表上下移动，Enter 进入
  • c 对比选中项，r 重跑，/ 搜索
  • 所有对话框 Esc 关闭，焦点归还触发元素

你是主要用户且每天用它，键盘效率的收益会被放倍。

长任务的反馈

  • 提交后立刻返回 job_id 并跳转到详情页，不做转圈等待
  • 详情页显示当前阶段（拉镜像 / 准备工作区 / 运行中），而非笼统的「处理中」
  • 预计剩余时间基于历史同类任务的中位数，而非线性外推
  • 可关闭页面，完成后通知

可访问性底线

  • 颜色不作为唯一信息载体（状态同时有图标与文字）
  • 对比度满足 WCAG AA（深色主题尤其要检查次要文字）
  • 所有图表提供数据表切换视图
  • 焦点可见环、跳到正文链接、语义化标签

「颜色不唯一」这条对色觉障碍者是必需，对所有人则意味着截图分享时信息不丢失。
